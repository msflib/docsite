    Testing and deployment¶

    Tests¶

    bash tests-start.sh

    This creates ./tmp and ./uploads, runs app/tests_pre_start.py, then runs scripts/test.sh, which calls pytest with coverage over app/tests. PYTEST_XDIST_WORKERS sets the number of pytest-xdist workers: unset means auto (one per CPU), a number sets that many, and an empty value, 0, false or off runs the tests serially. Extra pytest arguments go after the script name.

    pyproject.toml loads MSFLib's fast_bcrypt pytest plugin, which hashes passwords at bcrypt's minimum cost in tests. Without it, every account a test creates costs about a quarter of a second.

    How the suite is set up (app/tests/conftest.py):

    • Each xdist worker uses its own SQLite file in ./tmp, so the tests do not need PostgreSQL.
    • The session fixture recreates the tables and first data (init_db(create_tables=True)) for every test.
    • The client fixture overrides get_session and get_keystore with the test session and an in-memory key store.
    • superuser_account_token_headers and normal_account_token_headers return ready-made authorisation headers using helpers from msflib.utils.tests.account.
    • mock_send_email patches msflib.services.email.send_email.

    The tests cover login, the admin account routes, first-run data and the seeders. test_celery.py is skipped. Write new tests under app/tests/, mirroring the app/ layout.

    CI (.github/workflows/pytest.yml) runs the suite on pull requests to dev or main only when the pull request has the ready-for-analysis label. ruff.yml and flake8.yml run the linters on every pull request. Locally, pre-commit install sets up the same checks, and scripts/lint.sh, scripts/format.sh and scripts/format-imports.sh run them on demand.

    Docker¶

    The Dockerfile builds in two stages. The builder installs the dependencies into /app/.venv (using scripts/toml_deps.py to rewrite the MSFLib git dependencies to local paths, with CONTAINER_GITHUB_PAT as a build argument if the repository needs authentication), and the final image copies the result and starts uvicorn app.main:app on port 8000.

    Two details:

    • The image copies .env-test to .env, so a container started without environment variables runs with the test configuration. Provide real values at run time through environment variables, and never rely on the baked-in SECRET_KEY. Real environment variables take precedence over .env.
    • .env-test also sets INITIAL_DATA_RESET_DB=True. If you run prestart.sh (or app.initial_data) in a container with production database credentials, set INITIAL_DATA_RESET_DB=false at run time first, or initial_data drops and recreates every application table.
    • The image runs only the web process. It does not run prestart.sh; run it as a separate step or override the command to call it first.

    ./build-container.sh <tag> <registry> builds the image, logs in to the registry and pushes it as <registry>/<tag>:latest.

    Readiness check¶

    A container can be up and still unable to do its job: the database is at an old revision, SECRET_KEY was never set, the Redis password is wrong. MSFLib's readiness engine answers one question before you send traffic to a deployment: which requirements are met, which are not, and what to do about each. It is read-only unless you pass --fix. The checks and options are described in Readiness checks.

    Needs a newer core

    msflib.core.readiness is not in core-v0.2.1, the version pyproject.toml pins today. Move the msflib pin (and the module pins, which depend on it) to the release that ships it before you add the steps below.

    Add the suite¶

    Create app/readiness.py:

    from msflib.core.readiness import Suite

from app.core.config import settings
from app.db.session import engine

suite = Suite.from_settings(settings, engine=engine, name="my-app")

    Suite.from_settings collects core's own checks (settings, database, storage) plus the checks of every MSFLib module whose settings class AppSettings inherits. When you add msflib-ingestion, msflib-knowledge or msflib-ai-core to AppSettings, their checks (broker and worker, graph and vector extensions, provider calls) join the run without further wiring. The schema-at-head and drift checks run only when you pass migration= (an msflib.db.migrations.MigrationConfig); the example above omits it, so it does not verify migrations. The template has no MigrationConfig on this branch, so add one before relying on that check. Use unmanaged_tables=[...] for tables your models do not own.

    Run it on every deploy¶

    Run it after prestart.sh (which waits for the database, migrates and creates first data) and before the new version takes traffic, with the production profile:

    prestart.sh on this branch

    prestart.sh runs python ./app/initial_data.py, which uses relative imports and fails when run by path. Run it as python -m app.initial_data (or use the version of prestart.sh that does) before the readiness step; otherwise the step never starts.

    python -m msflib.core.readiness --suite app.readiness:suite --profile prod
    Exit code Meaning Deploy step
    0 ready continue
    10 ready, with warnings continue, and read the warnings
    1 not ready stop and fix; the report lists root causes first, then the steps in order

    Guidelines:

    • Run it where the app runs. Use the same image, environment variables and network as the web process (for example docker run --rm --env-file ... <image> python -m msflib.core.readiness ...). A check run from a laptop proves nothing about the server's Redis or database.
    • Use --profile prod in production. Some checks only matter there: ENVIRONMENT, an explicit SECRET_KEY, and SQLite being unacceptable.
    • Treat 1 as a failed deploy and 10 as a decision. Do not turn warnings into a pass by ignoring the exit code; a skipped check (--offline, a missing engine) is itself reported as a warning so a partial run is never a plain READY.
    • Keep a time limit. Every check has its own timeout. --timeout SECONDS lowers it for the whole run (it never raises one), which keeps a pipeline step from waiting on a hung dependency.
    • Use --json in automation. It prints one versioned document (verdict, exit_code, findings[], plan[]) to archive with the deploy.
    • Use --offline for pipelines without access to paid providers. It skips the checks that call an external service.
    • On macOS, add --isolation process to get the same containment as on Linux (a timed-out check is killed). The default there is a thread.
    • Read the output as data. Provider keys and URL passwords are masked in everything it prints, but do not paste a report into a public channel without looking at it first.

    Fixing with --fix¶

    --fix shows what each safe remedy will change, asks, applies it and re-checks. --yes skips the question but not the preview, and --dry-run only shows the plan. It only applies remedies that are idempotent and never delete anything: core.migrate is offered only when the pending migrations are recognisably additive, so a migration that drops or rewrites data is left to you. Run it by hand, not as an unattended pipeline step, and review the plan first. --fix --json needs --yes or --dry-run, because nothing can ask.

    The template's .env-test sets INITIAL_DATA_RESET_DB=True; that variable is separate from readiness, but it is the reason to check your production environment first (see Docker).

    The knowledge module's extension provisioning needs a PostgreSQL superuser connection in READINESS_PG_SUPERUSER_DSN; without it the check prints the equivalent psql commands for you to run.

    Add your own checks¶

    Application checks live in app/readiness.py next to the suite: create a Registry("app"), add checks with @registry.check(...), and pass it as extra=[registry] to Suite.from_settings. A check must be read-only, declare what it needs with requires=, and return an Outcome with the steps that fix a failure. The rules, helpers and a worked example are in Write a check.

    Worker¶

    app/worker.py defines a Celery app named app.worker with the default queue main-queue and one example task. worker-start.sh waits for the database and starts a worker on that queue. Without REDIS_HOST the broker is memory://, which only works inside one process, so a separate worker needs Redis. For how MSFLib runs long jobs and which pieces use the worker, see Long-running jobs and ingestion.
