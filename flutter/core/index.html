    Core¶

    The kh_core package contains the shared domain and infrastructure primitives that the rest of the library is built on. It is intentionally designed to be as close to pure Dart as possible, so it can be used in tooling, tests, and platform code without requiring the Flutter SDK for every situation.

    Package purpose¶

    kh_core is responsible for:

    • app environment definitions and bootstrap config
    • result/failure error modeling
    • base entities and repository contracts
    • validation and utility extensions
    • common retry, debounce, and pagination helpers

    Status¶

    This package is under active development and is a foundational dependency for the later packages in the monorepo.

    Installation¶

    dependencies:
  kh_core:
    git:
      url: https://github.com/msflib/flutter.git
      path: packages/kh_core

    Main exports¶

    Symbol Purpose
    KhEnvironment enum for environment values such as development/staging/production
    KhEnvironmentConfig app-level environment configuration loaded once at bootstrap
    KhResult<T> typed success/failure return model
    KhFailure root failure type for typed errors
    KhException thrown exception model for infrastructure code
    KhEntity<I> base entity with identity semantics
    KhPage<T> paginated collection model
    KhReadRepository<T, ID> read-only repository contract
    KhMutableRepository<T, ID> write-capable repository contract
    KhDebouncer debounced repeated actions
    KhRetry retry wrapper for failure-prone operations

    Environment setup¶

    Bootstrap once at app startup:

    import 'package:kh_core/kh_core.dart';

void main() {
  KhEnvironmentConfig.initialize(
    KhEnvironmentConfig(
      environment: KhEnvironment.fromString(
        const String.fromEnvironment('ENV', defaultValue: 'development'),
      ),
      apiBaseUrl: const String.fromEnvironment('API_BASE_URL'),
      enableLogging: true,
    ),
  );

  runApp(const MyApp());
}

    This pattern allows the application to read the same configuration from all layers without passing environment values around manually.

    Result and failure handling¶

    The library uses KhResult<T> to model operations that may succeed or fail without relying on exceptions as the primary return type.

    import 'package:kh_core/kh_core.dart';

KhResult<String> fetchName() {
  try {
    return const KhResult.success('Ada');
  } on Exception {
    return const KhResult.failure(
      KhValidationFailure('Unable to fetch user name'),
    );
  }
}

final result = fetchName();
final text = result.fold(
  onSuccess: (value) => value,
  onFailure: (failure) => failure.message,
);

    This makes domain code and UI logic much easier to reason about when the same method can either return data or an explicit failure.

    Base entity model¶

    Use KhEntity<I> for domain objects with a stable identifier:

    class User extends KhEntity<String> {
  const User({required this.id, required this.name});

  @override
  final String id;

  final String name;
}

    The identity is used for equality semantics rather than every field being compared.

    Pagination and repository contracts¶

    KhPage<T> makes list handling consistent across the library:

    final page = KhPage<User>(
  items: const [User(id: '1', name: 'Ada')],
  page: 1,
  pageSize: 20,
  totalCount: 1,
);

if (page.hasNextPage) {
  // continue fetching
}

    Repository interfaces are deliberately small and composable:

    abstract class UserRepository implements KhMutableRepository<User, String> {}

    Common utilities¶

    kh_core also exposes a small set of everyday helpers for formatting, validation, retry, and timing.

    final validEmail = 'ada@example.com';
final isEmail = KhRegex.email.hasMatch(validEmail);

final debouncer = KhDebouncer(const Duration(milliseconds: 300));
debouncer.run(() => print('debounced'));

    Troubleshooting¶

    • Call KhEnvironmentConfig.initialize() before reading KhEnvironmentConfig.current.
    • Use KhResult.guard or KhResult.guardAsync for conversion between thrown exceptions and typed failures.
    • Prefer explicit domain failures over generic errors when the cause matters to the caller.
