    Scopes, tenancy and workspaces¶

    Most MSFLib data belongs to someone: a tenant, a workspace inside it, sometimes an individual account. A scope is the small immutable object that says who a call is acting for. It is built once at the endpoint boundary and passed down, so services, config lookups and storage keys all agree on the same identity.

    Three tiers recur throughout:

    Tier Identifier Provided by
    Tenant tenant_id msflib-tenancy
    Workspace workspace_id msflib-workspaces
    Account (user) account_id msflib-account and msflib-auth

    ScopeEnvelope¶

    A ScopeEnvelope tracks the full context of one request and is threaded through the layers until it reaches the code that filters with it, usually an action. It is created only from a request, at its boundary; background work on a stored record uses the record's placement instead.

    ScopeEnvelope lives in msflib.scope. It is a frozen dataclass with four parts:

    Part Holds
    scope Where the request is: a TenantScope (tenant_id: int, workspace_id: int | None) or a module's subclass of it
    principal Who is calling: a PrincipalContext with an int account_id, or None for a service call. Its roles are read from the site's RoleLookup when a role check decides, not carried here
    attributes Policy inputs that are not dimensions, such as the channel
    metadata Request tracing data 
    from msflib.scope import PrincipalContext, ScopeEnvelope, TenantScope

envelope = ScopeEnvelope(
    scope=TenantScope(tenant_id=1, workspace_id=None),
    principal=PrincipalContext(account_id=5),
)
envelope.scope
# TenantScope(tenant_id=1, workspace_id=None)
envelope.principal.account_id
# 5
envelope.dimensions
# {'tenant_id': '1', 'workspace_id': None}

    scope is the source of truth. dimensions is its string view, built once when the envelope is created, in the form the compiler writes into storage keys and filters. You never pass dimensions in. Every field of the scope is a key, and None stays None: for workspace_id that is the workspace-less bucket (see below). Text is trimmed on the scope itself, so a filter and a key read the same value. An id field must hold a row id, so ScopeEnvelope(scope=TenantScope(tenant_id=0, workspace_id=None)) raises ScopeValidationError.

    The account appears in two places, and they mean different things:

    • principal.account_id is who is calling. A check (a role, a membership, a permission) asks the principal.
    • account_id in the scope is an account's own space that the request runs in: its user-tier settings, a memory namespace kept apart per account, or a member's records an admin opens. It is a dimension like workspace_id, registered by core, and it is present only when the operation runs in an account's space.

    A request's base envelope always has the caller on its principal and no account in its scope: the boundary never stamps it. An operation that runs in an account's space adds it where its envelope is built, the principal's account for the caller's own space or an access-checked selector for another account's: envelope.extend(AccountScope, account_id=envelope.principal.account_id). The two fields can hold the same id and still stay separate: code that filters or keys reads the scope, and code that checks reads the principal. Extending to a scope type with no field for a value the scope holds raises instead of dropping it.

    Envelopes are immutable. A module that needs more dimensions (conversation_id, project_id, ...) declares a scope type with those fields and builds it from the request's envelope (see Typed scopes).

    Getting the scope in an endpoint¶

    get_scope_dependencies returns a DependencyNamespace with one FastAPI dependency, get_base_envelope, which builds the request's envelope from the site's resolved identity. The envelope is a fact of the request, so there is one per request. You pass in your site's own get_current_* dependencies (from auth.get_account_dependencies, auth.get_user_dependencies and tenancy.deps.get_tenant_dependencies).

    from fastapi import Depends
from msflib.scope import ScopeEnvelope, get_scope_dependencies

scope_deps = get_scope_dependencies(
    get_current_tenant=get_current_tenant,
    get_current_workspace=get_current_workspace,
    get_current_account=get_current_account,
)


@router.get("/items")
def list_items(envelope: ScopeEnvelope = Depends(scope_deps.get_base_envelope)):
    return item_service.list_for_scope(envelope.scope)

    Its scope is the tenant and the workspace (None is the workspace-less bucket); its principal is the current account. An operation narrows it from there: a module's selectors (conversation_id), facets, or the account it runs in.

    The callables follow one rule:

    • get_current_tenant and get_current_account are required. A site that does not deal with tenancy passes the get_current_tenant from get_tenant_dependencies (see Tenants), which resolves the default tenant.
    • get_current_workspace is required here and in every router and dependency factory that takes identity (API-7). A workspace that resolves to None is the workspace-less bucket: the tenant level, inside no workspace, never "any workspace". A site without workspaces passes msflib.scope.no_workspace, and so do routes at the tenant or account level on a site that has them (the workspaces router, auth.get_account_dependencies), so the absence is stated.
    • get_scope_ids(...) is deprecated in core 0.3.0 and removed in the next minor; read the typed scope from envelope.scope instead. It takes the same callables and returns account_id, tenant_id and workspace_id dependencies that yield plain ids and fail closed (401 for no account, 404 for no tenant or a workspace of another tenant); workspace_id is None for the workspace-less bucket. Routers use it instead of unpacking .id in each endpoint.
    • None of them checks membership. An operation lists MembershipConstraint(dimension) in its profile's constraints, and its envelope dependency runs them on the envelope, with the check the container's module registered in MEMBERSHIP_REGISTRY (see Operations and permissions). It answers 401 for a missing caller and 403 for a non-member. Routers still use the deprecated get_member_account_dependency(..., get_current_tenant=..., is_workspace_member=...), where the check is msflib.workspaces.is_workspace_member (active memberships by default) or allow_any_member for a host without membership rules. It answers 404 with no workspace or a workspace of another tenant, and 403 for a non-member.

    Compiling a scope¶

    DimensionCompiler turns an envelope into a key string, segments or a mapping, validating it against a named operation profile first. It compiles only once the dimension registry is locked, which register_dimensions(settings) does when the process starts (see Your own dimensions).

    from msflib.scope import AccountScope, DimensionCompiler, register_dimensions

register_dimensions(settings)  # once, when the process starts
compiler = DimensionCompiler()
compiler.register_profile(
    "items.search",
    {"required": ["tenant_id"], "required_nullable": ["workspace_id", "account_id"]},
)
# The items are kept per account; this operation runs in account 5's own space.
keyed = envelope.extend(AccountScope, account_id=5)
compiler.compile_string(keyed, operation="items.search")
# 't/1/a/5/w/-'
compiler.compile_map(keyed, operation="items.search")
# {'tenant_id': '1', 'account_id': '5', 'workspace_id': '-'}
compiler.compile_map(keyed, operation="items.search", use_sentinel=False)
# {'tenant_id': '1', 'account_id': '5', 'workspace_id': None}
compiler.compile_string(envelope, operation="items.search")
# 't/1/a/-/w/-': the request envelope holds no account

    A profile lists required dimensions, required-but-nullable dimensions and optional ones. In items.search above tenant_id is required, so compiling an envelope without a tenant raises ScopeValidationError; workspace_id and account_id are nullable and compile to the sentinel - when null. A new ProfileRegistry is empty: core registers no profile for a data operation, and the one profile it does register, guard.check, lives in the guards' own registry (msflib.guard.scope). Register a profile for each of your operations on the compiler (register_profile). Modules do this for theirs in their scope_profiles.py: ai_core registers its aicore.* operations (aicore.retrieval, aicore.memory, aicore.checkpoint and others), and msflib.workspace_config.scope_profiles defines workspace_config.storage_key, where tenant, workspace and account are all required-but-nullable, so a tenant-tier row can have a null workspace and a workspace-tier row a null tenant.

    Behaviour may change (#267)

    Scope profiles currently require tenant_id but allow a null workspace_id, so the two dimensions are not treated symmetrically. Whether the profiles should treat the two the same is undecided.

    You can also evaluate access rules over a scope with the constraint classes exported from msflib.scope (MembershipConstraint, RoleConstraint, PermissionConstraint, AnyConstraint, ConstraintEvaluator). A constraint is evaluated with evaluate(envelope, *, session=None): it reads where the request is from envelope.scope, who is calling from envelope.principal and policy inputs from envelope.attributes, and takes the database session as an argument when it reads rows. There is no separate evaluation context. A guard narrows the envelope's scope to the tier it checks at (msflib.guard.narrow_envelope). MembershipConstraint takes a dimension and reads the check registered for it. AnyConstraint allows when any of its constraints does. An operation's profile lists them in constraints, and its envelope dependency runs them for a route (see Operations and permissions). ConstraintEvaluator.for_operation(profile_registry, operation) builds an evaluator that runs the profile's constraints at the profile's enforcement level, and permits(envelope, session=...) says whether the request goes on: an allow, or a deny the level only records (log-only, shadow). Roles are tier-qualified RoleKeys (written tier:key, for example tenant:admin, when serialized). RoleConstraint allows a caller holding any of the RoleKeys it is given, as the site's one RoleLookup (registered and locked in msflib.scope.ROLE_LOOKUP_REGISTRY at startup) returns them for the caller at envelope.scope; it never reads roles off the principal. PermissionConstraint asks a PermissionResolver (authz's RoleService) whether the caller holds a permission key at a tier. Profiles and ConstraintEvaluator enforce by default; log-only and shadow are an explicit choice, and a profile that lists constraints at either level logs a warning when it is registered.

    Behaviour may change (#270)

    The AI API's own profiles choose log-only explicitly, as a rollout exception to the enforce default: a failing constraint there is logged rather than rejected unless SCOPE_CONSTRAINTS_ENFORCE is set. Whether those profiles should move to enforce is undecided.

    Operations and permissions¶

    An operation is what a request does: documents.read, documents.manage. A permission is something a caller holds, and it is one of the grants an operation can need. The others are memberships and roles. An operation's profile lists the dimensions its scope holds and the grants it needs, so the endpoint names only the operation:

    # documents/scope_profiles.py
from msflib.scope import MembershipConstraint, PermissionConstraint, ProfileRegistry, RoleTier

PROFILE_REGISTRY = ProfileRegistry()
PROFILE_REGISTRY.register(
    "documents.manage",
    {
        "required": ["tenant_id"],
        "required_nullable": ["workspace_id"],
        "optional": ["account_id"],
        "constraints": [
            MembershipConstraint("tenant_id"),
            MembershipConstraint("workspace_id"),
            PermissionConstraint("documents.manage", tier=RoleTier.workspace),
        ],
    },
)

    # documents/router.py, inside the router factory
from msflib.guard import build_operation_envelope_factory

get_operation_envelope = build_operation_envelope_factory(
    profile_registry=PROFILE_REGISTRY,
    get_envelope=scope_deps.get_base_envelope,
    get_session=get_session,
    # msflib-authz's RoleService, or RolePermissionResolver(ROLE_PERMISSION_MAP)
    # on a site without authz
    resolver=role_service,
)

@router.delete("/documents/{document_id}")
def delete_document(
    document_id: int,
    envelope: ScopeEnvelope = Depends(get_operation_envelope("documents.manage")),
    session: Session = Depends(get_session),
):
    document_service.delete(session, envelope.scope, document_id)
    • get_operation_envelope(operation) returns the operation's dependency. It is built once per operation, when the route is declared, so an unknown operation, a membership with no registered check, a permission with no resolver or whose resolver is not ready, or a role check without a registered, locked role lookup stops the app at startup. A guard and auth's RoleCheck and WorkspaceRoleCheck refuse to start the same way.
    • For each request it takes the envelope get_envelope builds (401 for no caller, 404 for no tenant or a foreign workspace). It checks the envelope against the dimensions the profile lists and answers 404 when a required one is missing or one is not allowed. It then runs the profile's constraints in order at the profile's enforcement level, and answers a denial with 403.
    • A profile lists PermissionConstraint(key, tier=) and RoleConstraint(roles) without saying who answers. The builder binds the host's resolver to each permission: the site's one answer to who holds a permission key. That is msflib-authz's RoleService, which reads each role's permissions, or, on a site without authz, msflib.guard.RolePermissionResolver(ROLE_PERMISSION_MAP), which grants a key to a caller holding a role listed for it at or above its tier. Never both: on an authz site the roles that grant a key are those whose permissions include it. A permission is asked at its tier: a tenant-tier permission is checked at the tenant, whatever workspace the request is in. A RoleConstraint reads the site's one role lookup, which the host registers at startup with ROLE_LOOKUP_REGISTRY.register(...) and then locks with ROLE_LOOKUP_REGISTRY.lock(), so it cannot change after routes are built: msflib-auth's role_lookup for role attributes, or msflib-authz's build_role_lookup(...) for assignments. Every role check reads it, so a caller holds the same roles whichever route asks. AnyConstraint([...]) accepts any one of the grants it holds, and each is bound the same way.
    • An operation whose scope holds selectors passes its own envelope source: get_operation_envelope("conversation.read", get_envelope=get_conversation_envelope).
    • To change what an operation needs, change its profile. A host that wants different grants for a module's operation registers the operation again before it builds the module's router; the endpoint stays as it is.
    • Where an operation needs exactly one permission, give both the same name. They differ when one permission covers several operations, or when an operation needs none.

    A route that needs one permission and has no operation of its own names the key instead: dependencies=[Depends(guard("notifications.manage", tier=RoleTier.tenant))], with guard from msflib.guard.build_guard or authz's get_authz_dependencies. It is the short form of an operation with that one grant. A route takes an envelope dependency or a guard, never both.

    Code that runs inside a request, such as an agent tool holding the request's envelope, checks another operation with ConstraintEvaluator.for_operation(PROFILE_REGISTRY, "documents.read").permits(envelope, session=session). That works for an operation whose profile lists no permission: a PermissionConstraint without a resolver denies. A service never builds an envelope, and a job or worker checks no grant: it acts on a row's placement.

    Who grants a permission key¶

    A permission key is granted to roles in one of two ways, and a site uses exactly one. The host picks it by the resolver it passes to the guard builders.

    Role-permission map (msflib.guard.ROLE_PERMISSION_MAP) Role-permission model (msflib-authz)
    Where it lives In code, in the process In the database (Role, RolePermission rows)
    Who writes it Modules, at import: ROLE_PERMISSION_MAP.register("things.manage", roles=[...]) Seeded once at startup (seed_role_permissions), then changed at runtime through RoleService (create_role, add_permissions), for example from an admin tool the host builds
    Changing it A code change and a deploy A data change; no deploy
    Roles it names The roles a RoleLookup returns: auth's attribute roles (platform:root, tenant:admin, workspace:owner, ...) The roles assigned in authz, which may include custom roles
    Resolver RolePermissionResolver(ROLE_PERMISSION_MAP) RoleService
    Site Without authz With authz

    On an authz site the map does not count: the roles that grant a key are those whose permissions include it, so what an admin changes in the database is the whole answer. A site moving to authz gives its roles the keys as permissions (seed_role_permissions, or RoleService.add_permissions) and stops relying on the map.

    Typed scopes¶

    Code that filters rows takes the envelope's scope, passed down unchanged. TenantScope (tenant_id: int, workspace_id: int | None) is the shared shape. A module that needs more dimensions subclasses it and does not redeclare the identity pair. A row's own tenant and workspace is its placement, not a scope: read it with TenantPlacement.of(row) and stamp a new row with placement.column_values() (msflib.scope.TenantPlacement). envelope.extend(ScopeType, **selectors) returns the envelope with its scope extended to the module's type: each field takes the selector you pass, else the value the envelope's scope holds, else its default. The principal, attributes and metadata are kept. A value the envelope's scope holds that the new type has no field for is never dropped silently: extend raises ScopeValidationError naming it, whether it is a facet (in a Facets field or a field of its own), an account or a restriction such as private_to_account_id. The typed scope has no static check for this, so the error is the check. Extending the other way carries the facets into the new type's fields named like them (project_id, conversation_id), so a FacetScope and a module's typed scope convert in both directions. A field that holds nothing (None, no facets) is no loss:

    from dataclasses import dataclass

from msflib.scope import DimensionCompiler, TenantScope


@dataclass(frozen=True)
class ConversationScope(TenantScope):
    conversation_id: str
    sub_thread_id: str | None = None


compiler = DimensionCompiler()
compiler.register_profile(
    "chat.read",
    {
        "required": ["tenant_id", "conversation_id"],
        "required_nullable": ["workspace_id"],
        "optional": ["sub_thread_id"],
        "order": ["tenant_id", "workspace_id", "conversation_id", "sub_thread_id"],
    },
)
extended = envelope.extend(ConversationScope, conversation_id="c1")
compiler.validate_profile(extended, "chat.read")  # the operation's required dimensions
scope = extended.scope
scope.tenant_id  # 1, an int
scope.workspace_id  # None for the workspace-less bucket

    extend fails with ScopeValidationError, and validate_profile with a ScopeError subclass:

    • A selector must name a field of the scope class and hold the field's type. Nothing is parsed: an int field takes an int, not "7".
    • A null selector keeps None on a nullable field and is rejected on a non-nullable one. The field default applies only when neither a selector nor the envelope's scope supplies the field. A field with no value and no default fails.
    • validate_profile rejects a null required dimension and a set dimension the profile does not declare. Registering the profile with scope_class= checks the class against it at startup.

    ScopeEnvelope.build(ScopeType, principal=..., **dimensions) makes an envelope from dimension names and values, with the same checks.

    The type shares fields, not match semantics. Whether None means "only the workspace-less bucket" or something wider is decided by the action method that filters on it. See SCP-4 in the architecture guidelines.

    Membership checks¶

    Resolving a tenant or workspace does not prove the caller belongs to it. A router or guard that needs that takes MembershipCheck callbacks, one for the tenant and one for the workspace: check(session, *, account_id=..., container_id=...) -> bool. The module that owns the membership data supplies them and the host passes them in. A host with a single tenant or no membership rules passes allow_any_member explicitly; nothing in msflib assumes it.

    Your own dimensions¶

    Core registers the built-in dimensions (tenant_id, workspace_id, account_id, conversation_id, sub_thread_id and a few more) in msflib.scope.DIMENSION_REGISTRY. You add your own there with a DimensionSpec. One marked is_facet=True is a dimension rows are placed on. A request's facets live in one field, FacetScope.facets, keyed by the dimension's name, so a facet never becomes an attribute of the scope and cannot clash with tenant_id or a method.

    The basic case: register at import, use per request¶

    Most apps need only this. Register the dimension in a module your entry point imports before the routers, so it runs once at startup, and declare a typed key for code that reads it:

    # app/scope.py, imported by app/main.py
from msflib.scope import DIMENSION_REGISTRY, DimensionKind, DimensionSpec, FacetKey, NullMatch

DIMENSION_REGISTRY.register(
    DimensionSpec(
        canonical_key="site_id",
        kind=DimensionKind.row_id,  # an int row id; the default is text
        null_match=NullMatch.wildcard,  # a row with no site is read from every site
        is_facet=True,
    )
)
SITE = FacetKey("site_id", int)

    In an endpoint, add the value to the request's envelope and pass the result down:

    extended = envelope.with_facets(site_id=12)
extended.scope
# FacetScope(tenant_id=1, workspace_id=None, account_id=5, facets=Facets({'site_id': 12}))
extended.scope.facets.get(SITE)
# 12, typed int | None

    with_facets keeps the tenant, workspace, account and any facet already set; a None value removes one. Each value is checked against its spec when it is set: site_id="12" raises ScopeValidationError, as does a name that is not a registered facet. A facet cannot be named like a field of FacetScope or FacetPlacement (or a subclass of either): registering one raises DimensionConflictError, and a subclass that declares the name of a registered facet raises TypeError. Code that filters on every facet, as knowledge does, reads them all with scope.facets.items(). The key the compiler builds lists dimensions by priority and then by name, never by the order they were registered, so two processes that register in different orders build the same key. The msflib modules your settings compose register their dimensions when register_dimensions(settings) imports their scope_profiles, below; there is nothing else to import.

    Then load the dimensions of every module your settings compose when the application starts, after your own are registered:

    # app/main.py
import app.scope  # noqa: F401  registers site_id
from app.core.config import settings
from msflib.scope import register_dimensions

register_dimensions(settings)

    register_dimensions imports <package>.scope_profiles for every module your settings class composes, then locks the registry. A conflict between two modules stops the application at startup, not on the first request that reaches one of them, and the log lists the dimensions and facets the application runs with.

    Call register_dimensions in every process

    A DimensionCompiler compiles only against a locked registry: before the lock, every compile_string, compile_map, compile_segments and compile_items raises UnlockedRegistryError. A key compiled while dimensions can still be registered could differ from one compiled later, and a row written with it would not match a filter built afterwards, so the compiler refuses instead.

    What happens without the call:

    Process What fails
    The application The first request that compiles a scope key (a tiered config lookup, a document upload, an AI checkpoint or memory namespace, a provider or vector-store lookup, a vector-store search filter) fails with UnlockedRegistryError, a 500. Nothing fails at startup, so a deployment looks healthy until it serves one.
    A Celery worker Every job that compiles a key fails with UnlockedRegistryError and is marked failed after its retries. The worker is a separate process, so the application's call does not cover it: its entrypoint makes its own.
    A script or CLI (seeding, a one-off migration) The same error at the first compile. run_seed_cli(settings=...) makes the call for a seed command.

    With the call, in each process:

    • A conflict between two modules stops the process at startup, not on a request.
    • A module that registers a dimension after the lock raises LockedRegistryError (a RuntimeError), naming the dimension. A module whose settings you do not compose is not loaded by the call: compose its settings, or import its scope_profiles before the call.
    • Every process holds the same dimensions, so the application and its workers build the same keys.

    Tests lock the registry too, once registrations are done: DIMENSION_REGISTRY.lock() in a session fixture, or registry.lock() on a private one.

    A module with a dimension of its own¶

    A module registers its dimensions at module scope in its scope_profiles.py, beside its profiles:

    # inventory/scope_profiles.py
from msflib.scope import (
    DIMENSION_REGISTRY,
    DimensionKind,
    DimensionSpec,
    FacetKey,
    NullMatch,
    ProfileRegistry,
)

WAREHOUSE_DIMENSION = DimensionSpec(
    canonical_key="warehouse_id",
    key_alias="wh",
    priority=66,
    kind=DimensionKind.row_id,
    null_match=NullMatch.wildcard,
    is_facet=True,
)
DIMENSION_REGISTRY.register(WAREHOUSE_DIMENSION)
WAREHOUSE = FacetKey("warehouse_id", int)


def create_profile_registry() -> ProfileRegistry:
    registry = ProfileRegistry()
    registry.register(
        "inventory.count",
        {"required": ["tenant_id", "warehouse_id"], "required_nullable": ["workspace_id"]},
    )
    return registry


PROFILE_REGISTRY = create_profile_registry()

    A package's __init__.py is lazy, so import inventory registers nothing. warehouse_id is registered when inventory.scope_profiles is imported: by register_dimensions(settings) when the application composes the module's settings, or by your own import before that call when it does not (see the next section). It must be imported before the call, because the call locks the registry and a later registration raises LockedRegistryError. In msflib, knowledge registers project_id this way, in msflib.knowledge.scope_profiles.

    The advanced case: listing the facets at startup¶

    A DimensionCompiler may be built before every dimension is registered: it compiles in the order of the locked registry, and refuses to compile before the lock. Code that lists the facets does depend on timing: a profile that allows every facet, as knowledge's do, holds only the facets registered when it is built. If your app builds one at startup, load every dimension first: register your own, call register_dimensions(settings), then build. A package that composes no settings class is not found by that call, so import its scope_profiles yourself, as inventory is here. A profile registered with scope_class=FacetScope may name any registered facet.

    # app/scope.py, imported by app/main.py
import inventory.scope_profiles  # noqa: F401  registers warehouse_id
from app.core.config import settings
from msflib.scope import (
    DIMENSION_REGISTRY,
    DimensionCompiler,
    DimensionKind,
    DimensionSpec,
    FacetScope,
    NullMatch,
    ProfileRegistry,
    list_facets,
    register_dimensions,
)

DIMENSION_REGISTRY.register(
    DimensionSpec(
        canonical_key="site_id",
        key_alias="s",
        priority=65,
        kind=DimensionKind.row_id,
        null_match=NullMatch.wildcard,
        is_facet=True,
    )
)

# Every other module's dimensions, then the lock.
register_dimensions(settings)

facets = [spec.canonical_key for spec in list_facets(DIMENSION_REGISTRY)]
# ['conversation_id', 'warehouse_id', 'site_id', 'sub_thread_id']
PROFILE_REGISTRY = ProfileRegistry()
PROFILE_REGISTRY.register(
    "reports.export",
    {
        "required": ["tenant_id"],
        "required_nullable": ["workspace_id"],
        "optional": ["account_id", *facets],
    },
    scope_class=FacetScope,
)
compiler = DimensionCompiler(profile_registry=PROFILE_REGISTRY)

    extended = envelope.with_facets(warehouse_id=3, site_id=12)
compiler.compile_string(extended, operation="reports.export")
# 't/1/w/-/wh/3/s/12'

    Without the first import, facets would lack warehouse_id, and inventory would fail when it later tried to register it:

    msflib.scope.errors.LockedRegistryError: Dimension 'warehouse_id' was registered after the DimensionRegistry was locked. Register every dimension at import or startup: call msflib.scope.register_dimensions(settings) when the application starts, and register your own dimensions before that call.

    The scope.dimensions readiness check loads the same modules without locking anything, so a conflict shows up in python -m msflib.core.readiness too. Run on its own it cannot see the order your application imports modules in. It imports the modules as startup does: in a worker process (Linux) nothing outlives the check, and where checks run in a thread the imports and their registrations stay in that process, unlocked.

    Tenants¶

    msflib-tenancy provides the Tenant table (name, unique slug, status, a soft owner_account_id), TenantAction, and TenancySettings (namespace TENANCY, with DEFAULT_TENANT_SLUG and DEFAULT_TENANT_NAME, defaulting to "default" and "Default Tenant").

    Today the library runs single-tenant: one default tenant, resolved by slug. Rows that belong to a tenant carry a tenant_id foreign key to it (workspaces, for example). Three entry points matter to a host app:

    • TenantAction.ensure_default_tenant(session, settings=...) creates the default tenant if it is missing. Call it at startup. It is idempotent.
    • resolve_default_tenant_id(session, tenancy_settings=..., create_if_missing=True) returns its id, cached per process and database.
    • get_tenant_dependencies(session_dep=..., tenancy_settings=...) from msflib.tenancy.deps returns a namespace with get_current_tenant, which loads the default tenant row for a request and answers 500 if it was never seeded. Pass that to get_scope_dependencies. tenancy_settings= is required and takes the same settings.scope("TENANCY") you seed with, because it holds the configured DEFAULT_TENANT_SLUG.

    Importing the Tenant table class is done explicitly (from msflib.tenancy.models.tenant import Tenant), because the package root does not re-export it.

    If the scope carries a tenant_id, that value wins over any default lookup. A malformed tenant id raises ValueError rather than silently falling back to the default tenant (see msflib.tenancy.resolver.resolve_scoped_tenant_id).

    Resolving the caller's tenant from a request header or token, to choose among several tenants, is not implemented. get_current_tenant is the seam where you would add it.

    The workspace-less bucket¶

    workspace_id=None is a concrete, narrow bucket: rows that belong to no workspace. It is not "any workspace" and it is never a wildcard. Code that filters on scope matches it exactly:

    • Every profile msflib registers lists it as required-but-nullable and compiles it to the - sentinel.
    • The knowledge module's KnowledgeScope renders workspace_id=None as IS NULL.
    • ai_core's vector store profile lookup compares workspace_id == None explicitly, and its comments call this the catch-all workspace.

    When you write your own filters, do the same: pass None through to an IS NULL match. Dropping the clause when the id is None would widen the query to every workspace and leak data across them.

    The profile schema comments warn that null semantics for dimensions marked optional vary by consumer. Some, like ai_core's retrieval filter for conversation and sub-thread ids, deliberately let None widen the match. Check the consuming module before assuming either way.

    Access is through membership¶

    The tenant tables carry no roles or membership, and the scope dependencies never grant access on their own: an operation's profile lists the grants it needs, and its envelope dependency checks them (see Operations and permissions). Workspace access is decided by workspace membership and role checks from the auth and workspaces modules, for example the workspace_role_check(["admin"]) guard used by the workspace-config router. I found no code that gives a tenant-level principal blanket access to workspaces; if you need a tenant administrator who can act inside workspaces, model it explicitly (for instance by making that account a member of the workspace) rather than assuming the tenant tier implies it.

    Behaviour may change (#268)

    There is currently no tenant-admin role and no tenant-level workspace access, and no test pins this behaviour. Whether tenant administrators should get such access is undecided.

    Pitfalls¶

    • Build the scope from the authenticated caller at the endpoint, not from request parameters. A client-supplied workspace_id that nothing verifies is how data crosses workspaces.
    • get_base_envelope does not by itself prove the account belongs to the workspace on sites without a membership row.
    • Filter on envelope.scope, which holds typed values. envelope.dimensions is the string view for storage keys; do not parse it.
    • ScopeEnvelope is immutable and its mapping fields are read-only proxies. Make a new one instead of mutating.
