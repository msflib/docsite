    Contributing¶

    This section is for people changing MSFLib itself: internal developers and external contributors. If you are building an application on MSFLib, start with the Quick Start instead.

    Related pages: Releases and Writing docs.

    Repository layout¶

    MSFLib is a monorepo. Every package is versioned and released on its own.

    Path Contents
    core/ The base msflib package. Its release tags are core-v<version>. Its tests are in core/msflib/tests.
    modules/<name>/ One installable package per feature module, such as auth, account, tenancy, authz, ai_core.
    testsite/ A host application (testsite/app) that mounts the modules. Its tests are in testsite/app/tests.
    template/ Jinja templates used by scripts/scaffold_module.py.
    scripts/ Developer scripts: install_modules.py, scaffold_module.py, test.sh, lint.sh and others.
    .github/ Workflows plus the Python scripts the release workflows call.
    docs/ and mkdocs.yml This documentation site. See Writing docs.
    conftest.py, mypy.ini, .flake8, .pre-commit-config.yaml Repository-wide test and lint configuration. Ruff is configured in the root pyproject.toml.

    Dependency boundaries¶

    • core is standalone and must not import feature modules.
    • Feature modules may depend on core. Cross-module dependencies must be explicit and minimal, and each one is declared in the module's pyproject.toml.
    • Keep module APIs dependency-injected: no hardcoded app models or session globals.
    • Add or update tests for every behavior change.

    Development environment¶

    The root pyproject.toml declares Python >=3.10,<3.15. Use any version in that range; the repository does not pin one for the development virtual environment.

    Create a virtual environment and install the tooling:

    python3 -m venv .venv

    source .venv/bin/activate

    pip install --upgrade pip poetry

    poetry install

    The root project is not a package (package-mode = false), so poetry install does not install core or any module. It installs the repository tooling and test dependencies (pytest, ruff, flake8, mypy, pre-commit, alembic and similar), the root runtime dependency langchain-openrouter, and tomlkit, which the release scripts use. No root-level code imports langchain-openrouter; it is the package behind ai_core's optional openrouter extra (see modules/ai_core/pyproject.toml).

    Then install core and every module in editable mode:

    python scripts/install_modules.py

    install_modules.py must run inside an active virtual environment. It exits with a warning otherwise. It makes one pip install -e call for all selected packages, so dependencies resolve once. While it runs, it temporarily rewrites each module's pyproject.toml so that dependencies on other local packages resolve to the local directories instead of the pinned git tags. It restores the original files when it finishes. It then imports each package and prints where it was loaded from.

    Install only some packages with --modules. Names are space-separated, and core is a valid name:

    python scripts/install_modules.py --modules core auth

    Editable installs pick up ordinary source changes without reinstalling. Re-run the script when dependencies or package metadata change after you pull, or when you add another local package.

    Stale installed copies¶

    msflib is a namespace package: core and every module each ship a msflib/ directory. If site-packages holds a regular (non-editable) copy of msflib or of a module, for example from an earlier pip install of a git tag, Python can import that copy and your tests run old code without any error.

    Check where the packages load from:

    python -c "import msflib; print(msflib.__path__)"

    Every entry for core and for the modules you work on should point into this repository, not into site-packages. To fix it, re-run scripts/install_modules.py for the affected packages, for example --modules core. The script reinstalls them as editable. If a sibling module stops importing afterwards, re-run the script for that module too.

    The root conftest.py also prepends core/ and each modules/*/ directory to sys.path. That makes pytest run from the repository root prefer workspace code, but do not rely on it alone. Tools and scripts that run outside pytest do not get the same path.

    Running tests¶

    Run the whole flow with the wrapper script. It creates tmp/ and uploads/, runs core, each module, then testsite, one pytest process per suite, and prints a combined coverage report:

    ./tests-start.sh

    Pass extra pytest arguments through to every suite, for example -x -q. scripts/test.sh honors these environment variables: PYTEST_XDIST_WORKERS (off by default, for example auto), PYTEST_XDIST_DIST, PYTEST_SERIAL_MODULES and PYTEST_DISABLE_XDIST.

    Run a single suite directly. Tests live under msflib/<module>/tests inside each module:

    pytest core/msflib/tests

    pytest modules/auth

    pytest testsite/app/tests

    Run module suites separately

    Putting two or more module suites into one pytest process can fail from cross-suite pollution, such as shared tables, global registries and fixtures. This is why scripts/test.sh starts a separate pytest process per suite. Do the same locally: one suite per pytest command. A failure that only appears when suites are combined is not by itself evidence of a bug in your change.

    Test configuration:

    • The root conftest.py loads the msflib.utils.tests.fast_bcrypt plugin and prepends the local package roots to sys.path. There is no root pytest.ini, and the root pyproject.toml has no pytest section.
    • Some modules set pytest options in their own pyproject.toml. ai_core, ingestion and knowledge declare an integration marker for tests that need live services (credentials, a Redis broker, or Postgres with AGE and pgvector). Deselect them with -m "not integration".
    • Several modules set testpaths to msflib/<module>/tests.
    • CI runs the pytest workflow with Postgres enabled. testsite/docker-compose.yml defines a local Redis broker for the ingestion worker.

    Linting and typing¶

    Ruff, flake8 and mypy are configured at the repository root.

    • Ruff: configuration is in the root pyproject.toml (line length 100, rule sets such as E, F, I, UP, B, S, DTZ). E501 is ignored by ruff because the formatter owns line length.
    • flake8: .flake8 sets max-line-length = 100 and keeps E501 enabled, since the ruff formatter does not wrap long strings. CI scans ./core ./modules.
    • mypy: mypy.ini enables the pydantic.mypy and sqlmypy plugins, ignores missing imports and sets disallow_untyped_defs. The mypy hook is commented out in the pre-commit config, so mypy is not enforced automatically.

    Run them directly:

    ruff check core modules

    ruff format core modules

    flake8 core modules

    Install the pre-commit hooks once:

    pre-commit install

    The .pre-commit-config.yaml hooks are ruff-check (with --fix), ruff-format and flake8. The mypy and pytest hooks in that file are commented out.

    scripts/lint.sh is not a usable lint entry point for this repository. It runs mypy app, black app and isort --recursive against an app directory that does not exist at the root. Use the commands above.

    Commit and pull request conventions¶

    • Branch from dev and open the pull request against dev. Stabilization branches named dev-<major>.<minor>.x (for example dev-0.1.x) carry fixes for older minor lines. Do not commit to either branch directly.
    • Release commits made by automation use the chore(release): ... prefix and end with [skip ci]. Use a conventional-commit style prefix such as fix(ai_core): or docs: for your own commits. Recent history shows the pattern.
    • New pull requests are pre-filled from the organisation-wide template in the msflib/.github repository (.github/PULL_REQUEST_TEMPLATE.md), so it is not stored in this repository. Fill in the summary, type of change, related issues, how to test and the checklist. The template also has two optional sections: ## Documentation (list the pages you updated and any docs notices you removed; delete it if no docs changed) and ## Release Notes (keep it only if the PR carries a release:* label; see Releases).
    • Update the root README.md when functionality changes at a high level. Update the affected module's README.md and this docs site when install or usage changes.
    • Add a release:<module>:<patch|minor|major> label to a pull request that should publish a release when merged. Labels are described in Releases.

    What CI checks on pull requests to dev:

    Workflow What it does
    Ruff Analysis Calls the shared msflib/devops ruff workflow.
    Flake8 Lint Calls the shared flake8 workflow on ./core ./modules.
    Docs Check Runs when the PR touches docs/, mkdocs.yml, requirements-docs.txt, scripts/gen_api_reference.py, core/, modules/ or the workflow file itself. Fails if the generated API reference in docs/reference is out of date, then runs mkdocs build --strict and checks links. See Writing docs.
    Pytest Calls the shared pytest workflow with Postgres, but only when the PR has the ready-for-analysis label.
    SonarQube Analysis Runs only with the ready-for-analysis label.
    AI Augmentation Policy Runs .github/scripts/validate_ai_augmentation_policy.py, which checks that modules/ai_core/README.md keeps its policy sections and that four required ai_core test files exist and are not empty.
    Release Branch Guard Verifies that dev and at least one dev-<major>.<minor>.x branch exist, and that the PR base branch exists.
    AI Code Review Local test harness for the AI review action.

    Add the ready-for-analysis label when the pull request is ready, so the pytest and SonarQube jobs run.

    How modules are structured¶

    A module is a directory under modules/ with this shape, shown for auth:

    modules/auth/
  pyproject.toml
  README.md
  msflib/
    auth/
      __init__.py
      config.py
      deps.py
      router.py
      models/
      services/
      tests/

    Rules that matter:

    • Every package, core included, contributes to the single msflib namespace package. A module's code lives in msflib/<name>/ and is imported as msflib.<name>. Only core/msflib/__init__.py exists, and it extends the namespace path with pkgutil.extend_path. Do not add an __init__.py to a module's msflib/ directory.
    • Each module has its own pyproject.toml with a Poetry project named msflib-<name>, where underscores in the folder name become hyphens (ai_core is msflib-ai-core, workspace_notifications is msflib-workspace-notifications), and packages = [{ include = "msflib", from = "." }].
    • Dependencies on core and on other modules are git dependencies pinned to release tags. See Releases.
    • Tests live in msflib/<name>/tests and run from modules/<name>. Modules that declare testpaths there need no extra arguments.

    Adding a module¶

    Generate the skeleton from the template:

    python scripts/scaffold_module.py <module_name> --dry-run

    Run it again without --dry-run to write the files. module_name must be a valid Python identifier. --force overwrites an existing module directory, --install installs the new module in editable mode, and --quiet turns off step logging. The script renders template/ into modules/<module_name>/.

    After scaffolding:

    1. Edit the new pyproject.toml. Pin msflib (and any other dependency) to a release tag, never to rev = "dev"; the release workflows refuse to run while any manifest pins rev = "dev". Also replace the generated python = "^3.8" with the range core and the existing modules use, ">=3.10,<3.15".
    2. Install it with python scripts/install_modules.py --modules <module_name>.
    3. Mount its router in the testsite. testsite/app/api/api.py imports each module's router, for example from msflib.auth.router import router as create_auth_router. Add yours in the same way, and add any startup wiring to testsite/app/main.py.
    4. Add tests under msflib/<module_name>/tests. scripts/test.sh discovers a module's tests at modules/*/msflib/*/tests automatically.
    5. Add a docs page from the module page template and a nav entry. See Writing docs.
    6. Label the pull request release:<module_name>:<bump> if the module should be released when it merges.

    Working on authz¶

    modules/authz holds the roles, permissions and role assignments that other modules check. Read the authz module page first: it defines tier, owner and assignment scope, which are easy to confuse, and the rules below assume them.

    Protecting an endpoint or adding a permission¶

    • Name permission keys <module>.<action>, for example authz.manage_roles. Register them at import time with PERMISSION_REGISTRY.register(key, tenant_cascade=...) from msflib.authz, in the module that owns the feature. Decide tenant_cascade deliberately: True lets a tenant-tier role grant the permission inside any workspace of its tenant; False means only a workspace assignment (or a platform role) does.
    • Guard routes with require_permission(key, tier=...), or require_role(RoleKey(tier, key)) when the route names a role. RoleCheck and WorkspaceRoleCheck in auth stay supported as the simple attribute-based way; pick one way per route.
    • Do not seed role-permission bundles from your module. seed_role_permissions bundles whatever is registered when it runs, so the host app seeds after every module has been imported.
    • Test the guard at each tier it supports, including the denial cases (another tenant, another workspace, no assignment).

    Changing authz itself¶

    • There is one rule for "can this assignment grant authority". It is is_effective_assignment in msflib/authz/validation.py (tier shape, the role's owner scope, expiry), and every read path reaches it through RoleService._effective_assignments. Do not add a resolution query that loads assignments some other way, or a second copy of the rule. A new read path that skips it re-opens the gaps the rule closes.
    • Keep the owner and the scope apart in code and names. role_tenant_id / role_workspace_id is where a role is defined; assignment_tenant_id / assignment_workspace_id is where a grant applies. Never compare a role id with a request or assignment id as if they were the same thing.
    • Compare roles by RoleKey(tier, key), never by the bare key. The seeded admin exists at tenant and workspace tier, and a bare string cannot tell them apart.
    • Writes go through RoleService. Each public method is one closed unit of work (savepoints inside, one commit at the end; SVC-4), and events fire on that commit. Actions are plain data access and skip validation, so do not write roles or assignments through them outside tests.
    • Schema changes need a migration note. The module ships no migrations; host apps own them. A change to a table or constraint in msflib/authz/models must say so in the PR description and in Releases notes, and must keep create_all working for new databases.
    • Legacy support is transitional. The Account.role / User.type fallbacks in msflib/auth/deps.py and the two backfills in msflib/authz/seed.py exist only until assignments replace those attributes. Do not extend them; see the module page for how the two sources combine.

    Tests¶

    Tests live in modules/authz/msflib/authz/tests and run from modules/authz:

    cd modules/authz && pytest
    • The make_role and assign fixtures in conftest.py create rows directly, without validation. Use them to build deliberately invalid rows and check that resolution ignores them. Use RoleService to build valid ones.
    • When you change a rule, add the case to both the write test (grant rejects it) and the read test (a raw row that breaks it grants nothing).
    • The guards' tests are in modules/authz/msflib/authz/tests (test_deps.py, test_require_role.py, test_permission_guard_example.py). auth has its own tests for its attribute-based guards.

    Documentation and releases¶

    • When behaviour or a rule changes, update the tables on the authz module page in the same pull request. The valid and invalid combinations table is checked against the code, so keep it that way.
    • auth does not depend on authz, and authz does not depend on auth; identity arrives as injected callables. Modules that do depend on authz (for example drivelink, in the later parts of the series) pin its release tag. The pins between modules must be release tags, never rev = "dev"; see How modules pin each other. Release authz first, so that its dependents can pin its tag.
