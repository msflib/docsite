    Architecture and scoping¶

    Package boundaries¶

    ARC-1 · core never imports feature modules¶

    core/ is standalone. Feature modules under modules/ may depend on core; the reverse is never allowed. See also Dependency boundaries.

    ARC-2 · Hard dependencies on other modules are declared and few¶

    Every module depends on msflib core, and on msflib-tenancy when it has tenant_id foreign keys (MDL-6). A module may also hard-depend on another module when it genuinely needs it to work, for example documents on ingestion or knowledge on documents. Such a dependency is declared in the module's pyproject.toml, and only declared dependencies are imported at module scope.

    Before adding a new hard dependency, check whether the coupling can be optional instead. Integrate with modules a module can work without through:

    • structural Protocol contracts in contracts/,
    • injected callables (embedder, LLM and vector-store factories, as in ai_api's lazy callable factories),
    • eventbus hooks (ARC-4),
    • optional integrations/ packages guarded by is_importable (DEP-2).

    ARC-3 · Respect the layering¶

    router.py  →  deps.py / services/access.py  →  services/  →  actions.py  →  database
    Layer Owns Never
    router.py HTTP shape, status codes, wiring dependencies business rules, SQL, transaction composition
    deps.py request-scoped resolution: principal, path-param → row, access-checked context objects persistence
    services/ business rules, validation, orchestration, external calls building SQL
    actions.py queries and writes through ModelAction domain policy (SVC-2)

    The router should look the same whether or not a service composes several actions internally.

    ARC-4 · Integrate across modules through lifecycle events¶

    Prefer listening to another module's ModelAction lifecycle events (for example documentrecord-update-post-commit) over importing its services.

    ARC-5 · Relationship() only to tables the module can always import¶

    Relationships are allowed between tables owned by the same module, and to tables of a declared hard dependency (ARC-2), for example workspace_notifications mapping notifications' Notification. Foreign keys to a module that is optional or undeclared stay plain columns with explicit fetches: a relationship would force that module to be importable whenever the model is. Reference: modules/conversation/msflib/conversation/models/.

    ARC-6 · Fix shared gaps at the root¶

    When several modules need the same helper or workaround, put it in core and use it everywhere instead of adding a module-local copy. Examples: BaseEnum.__str__/__format__ (fixed in core rather than per-module .value guards), msflib.core.import_tools, msflib.actions.emit_after_commit.

    Why: local workarounds multiply. Four modules had independently written the same enum-formatting guard before it was fixed once in core.

    ARC-7 · Avoid duplication; reuse shared stacks¶

    Reuse the shared AI core, retrieval adapters, vector-store factory and scope metadata helpers. Keep ai_api/ai_core integration composition-based so middleware, policy and adapters can change without rewrites.

    Scoping¶

    SCP-1 · Scope is a core concern¶

    Scope lives in core/msflib/scope/. Use the canonical dimensions: tenant_id (organisation), account_id (user), and optional workspace_id. Use the existing scope compiler, policy and retrieval-filter adapters; don't build parallel scope implementations.

    A scope is the server-decided place a request runs, identified by those dimensions: it bounds which data is visible and what the actor may do. It is not a client selector (SCP-3) and not a row fact such as who defined a role or where a grant applies; those keep their own types even when the fields match. ScopeEnvelope is the boundary and policy form. Code that filters or authorizes uses a typed scope (SCP-4).

    SCP-2 · None is a real scope bucket¶

    workspace_id=None means "workspace-agnostic", a valid hard boundary, not "unscoped". Preserve explicit-null semantics when compiling and filtering.

    SCP-3 · Identity is bound server-side; selectors are authorized¶

    The isolation and identity dimensions (tenant_id, workspace_id, account_id) come from the server-side request context: the authenticated principal and the host app's resolvers. They are never taken from a client payload, a model or an agent tool argument.

    Resource selectors that narrow the scope, such as conversation_id and sub_thread_id in ai_api's requests, may come from the validated request, but they must pass an access check for the current principal before they are used (as conversation's ai_bridge access dependency does). A model or tool output never supplies either kind.

    Resolvers decide which tenant or workspace a request runs in; they do not check membership. A router or guard that needs it takes MembershipCheck callbacks (msflib.scope), one for the tenant and one for the workspace, supplied by the owning module and passed in by the host. It uses them for the caller (403) and for any account the request names (404). Don't fall back to a default tenant or to "any account" when a check is missing; a host that wants that passes allow_any_member.

    SCP-4 · Compile scope once, through the module's profile¶

    Register profiles in scope_profiles.py via ProfileRegistry with namespaced names ("<module>.<operation>"). Build the typed scope from the ScopeEnvelope with ScopeFactory.build(envelope, ScopeType, operation=...), once, at the request boundary, and pass it unchanged to every call below. TenantScope (tenant_id, workspace_id) is the shared shape: a module needing more dimensions subclasses it and does not redeclare the identity pair. Filter on the typed object, never on raw ScopeEnvelope.get_dim(...) calls, and don't parse dimension strings by hand. The type shares fields, not match semantics; an equality or hierarchical match belongs to the action method. Reference: knowledge/planner/scope_rewriter.py with contracts.KnowledgeScope, and ai_core/services/scope_metadata.py.
