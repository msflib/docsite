    Architecture and scoping¶

    Package boundaries¶

    ARC-1 · core never imports feature modules¶

    core/ is standalone. Feature modules under modules/ may depend on core; the reverse is never allowed. See also Dependency boundaries.

    ARC-2 · Hard dependencies on other modules are declared and few¶

    Every module depends on msflib core, and on msflib-tenancy when it has tenant_id foreign keys (MDL-6). A module may also hard-depend on another module when it genuinely needs it to work, for example documents on ingestion or knowledge on documents. Such a dependency is declared in the module's pyproject.toml, and only declared dependencies are imported at module scope.

    Before adding a new hard dependency, check whether the coupling can be optional instead. Integrate with modules a module can work without through:

    • structural Protocol contracts in contracts/,
    • injected callables (embedder, LLM and vector-store factories, as in ai_api's lazy callable factories),
    • eventbus hooks (ARC-4),
    • optional integrations/ packages guarded by is_importable (DEP-2).

    ARC-3 · Respect the layering¶

    router.py  →  deps.py / services/access.py  →  services/  →  actions.py  →  database
    Layer Owns Never
    router.py HTTP shape, status codes, wiring dependencies business rules, SQL, transaction composition
    deps.py request-scoped resolution: principal, path-param → row, access-checked context objects persistence
    services/ business rules, validation, orchestration, external calls building SQL
    actions.py queries and writes through ModelAction domain policy (SVC-2)

    The router should look the same whether or not a service composes several actions internally.

    ARC-4 · Integrate across modules through lifecycle events¶

    Prefer listening to another module's ModelAction lifecycle events (for example documentrecord-update-post-commit) over importing its services.

    ARC-5 · Relationship() only to tables the module can always import¶

    Relationships are allowed between tables owned by the same module, and to tables of a declared hard dependency (ARC-2), for example workspace_notifications mapping notifications' Notification. Foreign keys to a module that is optional or undeclared stay plain columns with explicit fetches: a relationship would force that module to be importable whenever the model is. Reference: modules/conversation/msflib/conversation/models/.

    ARC-6 · Fix shared gaps at the root¶

    When several modules need the same helper or workaround, put it in core and use it everywhere instead of adding a module-local copy. Examples: BaseEnum.__str__/__format__ (fixed in core rather than per-module .value guards), msflib.core.import_tools, msflib.actions.emit_deferred, msflib.db.batching.select_in (an IN over an id list of unknown length).

    Why: local workarounds multiply. Four modules had independently written the same enum-formatting guard before it was fixed once in core.

    ARC-7 · Avoid duplication; reuse shared stacks¶

    Reuse the shared AI core, retrieval adapters, vector-store factory and scope metadata helpers. Keep ai_api/ai_core integration composition-based so middleware, policy and adapters can change without rewrites.

    Scoping¶

    SCP-1 · Scope is a core concern¶

    Scope lives in core/msflib/scope/. Use the canonical dimensions: tenant_id (organisation), account_id (user), and optional workspace_id. Use the existing scope compiler, policy and retrieval-filter adapters; don't build parallel scope implementations.

    A scope is the server-decided place a request runs, identified by those dimensions: it bounds which data is visible and what the actor may do. It is not a client selector (SCP-3) and not a row fact such as who defined a role or where a grant applies; those keep their own types even when the fields match. ScopeEnvelope is the boundary and policy form. Code that filters or authorizes uses a typed scope (SCP-4).

    SCP-2 · None is a real scope bucket¶

    workspace_id=None means "workspace-agnostic", a valid hard boundary, not "unscoped". Preserve explicit-null semantics when compiling and filtering.

    SCP-3 · Identity is bound server-side; selectors are authorized¶

    The isolation and identity dimensions (tenant_id, workspace_id, account_id) come from the server-side request context: the authenticated principal and the host app's resolvers. They are never taken from a client payload, a model or an agent tool argument.

    Resource selectors that narrow the scope, such as conversation_id and sub_thread_id in ai_api's requests, may come from the validated request, but they must pass an access check for the current principal before they are used (as conversation's ai_bridge access dependency does). A model or tool output never supplies either kind.

    Resolvers decide which tenant or workspace a request runs in; they do not check membership. A router or guard that needs it takes MembershipCheck callbacks (msflib.scope), is_tenant_member and is_workspace_member, supplied by the owning module (msflib.tenancy, msflib.workspaces) and passed in by the host. It uses them for the caller (403) and for any account the request names (404). Don't fall back to a default tenant or to "any account" when a check is missing; a host that wants that passes allow_any_member. The same checks back MembershipConstraint and gate the tenant and workspace roles a role source returns (SCP-6). Never infer membership from the account's current_workspace_id; it is a preference, not a grant. Parameter names and order: API-7. Where membership is defined and enforced is moving to SCP-7.

    SCP-4 · Compile scope once, through the module's profile¶

    Register profiles in scope_profiles.py via ProfileRegistry with namespaced names ("<module>.<operation>"). A ScopeEnvelope holds the typed scope (envelope.scope), the caller (envelope.principal, with an int account_id) and the policy inputs; it is built once, at the request boundary, from typed values, and its dimensions are the string view of the scope for the compiler's sinks. Nothing converts a scope to strings and back (ADR 0009, A7). Build a module's own scope with envelope.extend(ScopeType, **selectors), once, at the request boundary, check it with DimensionCompiler.validate_profile(envelope, operation) where an operation requires dimensions, and pass it unchanged to every call below. The one derived scope is a guard's: a check below the workspace tier runs at the tenant's scope (msflib.guard.narrow_envelope(envelope, tier=), SCP-6). Request dependencies come from get_scope_dependencies; get_scope_ids is deprecated, and new code doesn't call it. TenantScope (tenant_id, workspace_id) is the shared shape: a module needing more dimensions subclasses it and does not redeclare the identity pair. Register the profile with scope_class= so it is checked against the dataclass at startup; the profile stays hand-written because one type can serve operations with different required dimensions. Filter on the typed object, never on raw ScopeEnvelope.get_dim(...) calls, and don't parse dimension strings by hand. A check asks who is calling from envelope.principal; a scope has an account_id field only where code filters or keys on it, as the boundary's AccountScope does. The type shares fields, not match semantics; an equality or hierarchical match belongs to the action method. The built-in id dimensions (tenant_id, workspace_id, account_id, private_to_account_id) accept only a row id, an integer from 1 to INTEGER_MAX, so an envelope whose scope holds 0, "7" or an out-of-range id is rejected when it is built, and PrincipalContext checks its account_id the same way. Every DimensionRegistry puts is_valid_row_id first in each id dimension's validators; a custom validator only adds checks. A module does not repeat that check. Reference: knowledge/planner/scope_rewriter.py with contracts.KnowledgeScope, and ai_core/services/scope_metadata.py.

    SCP-5 · Scope, placement and reach; tiers and facets¶

    Target design (msflib/fastapi#403)

    The vocabulary and naming rules apply now. These parts are planned, not yet in code: the shared per-facet filter helper and reach filtering in search. The existing filters were written before this rule and differ from one another: knowledge scoped_statement, documents list_for_scope, and ai_core retrieval metadata. #403 brings them in line.

    Each word has one meaning:

    Word Belongs to Meaning Examples
    *Scope a request Where the request is now. Server-decided, one value per request, held by the request's ScopeEnvelope as envelope.scope. TenantScope, ConversationScope
    *Placement a resource Where the resource lives. Set on write; changed only by promotion or a move. AccountPlacement adds the account the work is for, which tiered lookups resolve for. TenantPlacement, RecordPlacement, DocumentPlacement, AccountPlacement
    *Reach a grant Where the grant lets its holder act. A caller's reach is the union of the reach of their grants. RoleAssignmentReach, AIResourceReach, a ResourceAccess row
    *Tier the tenancy chain A level of platform → tenant → workspace. RoleTier
    *Owner a row Authorship only: who defined the row, not where it applies. RoleOwner

    To tell a resource from a grant: if you use it (a file, document, message, knowledge row, checkpoint), it is a resource and has a placement. If it tells you what you may use (a membership, share, role assignment, provider profile, config entry), it is a grant and has a reach. Sharing a file creates a grant with a reach; the file itself keeps its placement.

    A grant has a holder, a reach (where), a level (what) and a lifetime (expiry and revocation). Only live grants count towards reach. For stored grants on resources, authz owns all four: - holder: PrincipalKind (user, group; share link planned in #367). A share link is held by whoever presents its token, so the caller is anonymous and has no account_id. - reach and level: a ResourceAccess row with an AccessLevel. - lifetime: AccessService.revoke, and LinkService for links (planned in #367).

    Each comes from one source, and only that one:

    Created from Never from
    a ScopeEnvelope and its scope a request, at its boundary a row or a job
    a placement a resource row (TenantPlacement.of(row)), or the scope a new row is written in a grant
    a reach a grant row a resource row

    What the envelope is for. A ScopeEnvelope tracks the full context of one request (its scope, its principal, its attributes) and is threaded through the layers until it reaches the point that filters with it, usually an action. So before a function takes an envelope, ask what its final filter is for:

    • It limits what this request may see or do: thread the envelope to it.
    • It finds the rows that apply to a resource, the same way whether a request or a queued job asks: it takes that resource's placement. A request builds the placement at its boundary; a job builds it from its record.

    An envelope that is unpacked into a few ids just before the filter, or built from a row so a job can call a function, is a sign the function wanted a placement.

    A worker or an event handler has no request, so it has no envelope: it reads the placement of the row it acts for (msflib.core.records.PlacementReader reads one off any row). Two sites that handed ai_core's registry an envelope built from a record were removed in #401.

    Don't add core types for stored grants, or module types that duplicate authz's. A module may still define its own *Reach for reach it derives itself, such as KnowledgeReach from memberships (planned in #403) or AIResourceReach for provider profiles.

    • Name a tier enum, column or parameter *Tier or tier, never *Scope or scope_type. Parameters follow the type: reach=RoleAssignmentReach(), placement=..., not scope=.
    • scope names only the typed scope, which is envelope.scope, and a ScopeEnvelope is named envelope, in variables, parameters and dependencies, whether or not the code holds both. A dependency or builder is named for what it returns: get_scope and build_scope(envelope) return a typed scope; get_account_envelope and build_context_envelope return an envelope. Don't use another word for either, such as position.
    • ConfigTier (workspace_config) and ProviderTier (ai_core) also have a user level. That level is the account facet, not a tier: the tiers in those enums follow this rule, and #403 separates the account facet from them.
    • settings.scope("AI_CORE") is a settings namespace, not a tier. The scope dataclass a profile is checked against is passed as scope_class=.

    Tiers and facets. A scope dimension is either a tier or a facet.

    • Tier dimensions (tenant_id, workspace_id) form the only hierarchy. Roles and tiered grants apply downward along it: a tenant admin acts in every workspace of the tenant, and a platform provider profile applies to every tenant, with resolution falling back upward. In a filter, a tier dimension is an exact partition, and None is a bucket (SCP-2).
    • Facet dimensions are every other dimension: project_id, conversation_id, sub_thread_id, drivelink_id, and account_id as ownership. A facet is an independent filter, not a level below the workspace. Account is a facet, not a tier.
    • A facet may have a parent (sub_thread → conversation). The module's scope builder enforces it, and bindings close upward:
      • Binding a child binds its parents, using the child's own server-side row. A request that names a mismatched parent is rejected (SCP-3).
      • A placement stores its parents' ids as well.
      • Promotion clears a facet together with its descendants.
    • A resource tree (drivelink folders) is neither a tier nor a facet. A grant on a node also applies to that node's descendants. A none grant excludes a subtree from a wider grant. Authz resolves the grants nearest-ancestor-wins, so the nearest grant to a resource decides, including a none. Resolve tree reach through authz ResourceSharing (filter_readable, resolve_levels, list_shared, and filter_readable_for_link for an anonymous link caller, planned in #367); don't reimplement it.

    Access rule. A resource is visible when its tier partition equals the scope's and every facet chain passes. A chain (sub_thread → conversation → project) is checked once, at the deepest facet the resource is placed on; its parents aren't checked again, because reach to a child covers the rows its parents hold for it. A chain where the resource is placed on no facet passes. The checked facet passes when:

    Scope on the checked facet Resource placement on it Passes when
    bound to x x x is in reach (checked at the boundary, API-7)
    unbound any y y is in reach

    NULL never reaches this table. A resource with NULL on a facet is checked at the nearest parent it is placed on, or passes the chain when it has none. So a workspace-general resource stays visible from a conversation scope and from a workspace search, and a resource at (project P, conversation NULL) is visible in any conversation of P.

    Independent chains combine with AND by default; a module may declare OR between its own chains, never within one. Opening a conversation binds it, so sibling conversations stay out. Searching from a workspace leaves it unbound, so every reachable conversation is included and no other.

    • Search, whether SQL, vector or graph, applies reach inside the store query and never filters afterwards. A graph edge is returned only when both of its endpoints pass.
    • Reach comes from two kinds of grant. Derived grants are memberships, read through injected callables. A bound facet needs only a yes or no for its id (MembershipCheck, SCP-3). An unbound facet needs the ids the caller belongs to, from an injected membership listing that the owning module supplies (planned in #403), so the query filters by a known set and never by everything. Stored grants are authz rows: shares and share links through ResourceSharing, role assignments through RoleService. Both feed the same reach. A revoked grant must stop matching immediately, so reach from stored grants isn't cached across requests.
    • The match belongs to the action method (SCP-4). The scope, placement and reach types carry values, not rules. Action methods use one shared helper for the per-facet predicate, so modules don't diverge.
    • Before adding a type or Protocol for scope, placement or reach, check msflib.scope, msflib.guard and authz. A new one is justified only if all three hold:
      • two or more modules need it;
      • mixing it up is a correctness or security bug;
      • nothing already owns it.

    Principles for typed scopes:

    1. A scope encapsulates the dimensions that decide whether a principal may act, so signatures don't grow a parameter per dimension.

    2. A typed scope exists so that code can filter without converting and validating values at every layer. The ScopeEnvelope holds it as envelope.scope and is built once, at the request boundary, from typed values (ADR 0009 A7). Use the scope:

      • where an int-typed column is filtered;
      • where it is handed to an authorization protocol (RoleSource, PermissionResolver, a guard's narrow_envelope: SCP-6).

      Strings (checkpoint keys, memory namespaces, retrieval metadata, row keys) are encoded from the typed values by one compiler, whether they describe a scope, a placement or a reach (DimensionCompiler). Never convert typed values to strings and back. 3. Don't duplicate typed scopes: a different name with the same fields is a duplicate. One exception is deliberately decoupled modules (a soft dependency such as ai_api and conversation); the copy carries a comment saying so. A placement or reach with the same fields as a scope is not a duplicate, because it is a different concept (SCP-1). 4. Orthogonal concerns get orthogonal types: - where: TenantScope and its subclasses; - who: PrincipalContext, or a single account_id scalar (one dimension stays a scalar); - policy inputs: envelope attributes such as channel.

      Never put a principal, role or channel inside a typed scope. The ScopeEnvelope does carry the caller as principal, with the roles a RoleSource returns for the request's scope; a check asks the principal who is calling. A typed scope has a field if and only if code filters or keys on it: account_id is a scope dimension where rows or keys are separated per account (AccountScope), not as a way to say who calls. 5. A global (platform-level) profile or row applies everywhere and needs no request scope; creating one takes a reach, not a scope. A request scope always has a tenant and fails closed.

    SCP-6 · Authorization is a scope decision¶

    Target design (msflib/fastapi#391, amendment A5)

    This rule describes where authorization is going. build_guard, narrow_envelope, RoleSource and PermissionResolver are in code. Not yet: build_role_source, and RoleCheck and WorkspaceRoleCheck deciding through the evaluator (msflib/fastapi#397). Write new authorization code to this shape.

    • A role is RoleKey(tier, key) (msflib.scope.roles): the account role root is platform:root, any other account role is tenant:<role>, and a workspace user type is workspace:<type>. A role counts at its own tier and every tier below it.
    • Every allow or deny goes through ConstraintEvaluator and is a ScopeDecision, so denials are recorded the same way everywhere. Don't compare a role attribute or ask a resolver inline in a route.
    • Build an evaluator with ConstraintEvaluator.for_operation(profile_registry, operation, constraints), so its enforcement level comes from the operation's profile, and ask it permits(envelope, session=...). Pass enforcement= only to forward a host's rollout override, and don't map a decision to allow or deny by hand.
    • Guard routes with msflib.guard.build_guard. It takes a PermissionResolver (msflib-authz), role attributes mapped in ROLE_REGISTRY, or both.
    • RoleCheck and WorkspaceRoleCheck (msflib-auth) are the path for simple apps; they decide through the evaluator too. Recommend authz role-permission for enterprise and multi-tenant apps.
    • A role source gives the guard the caller's roles where the check runs: msflib.auth.roles.build_role_source for role attributes, and authz for assignments. build_guard takes it with role_registry. Pass is_tenant_member in a multi-tenant app, because an account has no tenant of its own.

    SCP-7 · Membership is a scope constraint¶

    Target design (msflib/fastapi#393, section 10)

    This rule describes where membership checks are going. The core pieces (MEMBERSHIP_REGISTRY, MembershipConstraint(dimension), build_envelope_dependency) land in msflib/fastapi#424. get_member_account_dependency is deprecated in 0.3.0 (warning raised at call time) and will be removed with no shim in 0.4.0, together with the hand-written membership copies in modules. Write new code to this shape where it can, using build_envelope_dependency once #424 is on dev.

    A membership is a grant whose reach is a whole container: a tenant, a workspace, a conversation, a project, a department. It is checked at the grant stage of the access stack (AUZ-12), by the same evaluator and in the same constraint list as roles and permissions. Tenant is not special, and every membership is defined and enforced the same way.

    • Defined by the owning module. The module that owns the container owns its dimension (DimensionRegistry), its membership rows and the query for them (its action), and its MembershipCheck, which it registers for its dimension at import time, the way documents registers its source adapters. Core holds only the protocol and the registry (ARC-1). A check is a fact about the container, so its owner registers it; where roles come from is the host's choice, so a RoleSource is passed to the guard builder, not registered.
    • A host replaces a check only to state a choice, such as allow_any_member for a site without membership rows, with one registry call at startup that passes replace=True. Registering a second check for a dimension without it is a startup error. The replacement applies wherever the dimension is checked.
    • A check answers one question, and the owner decides the answer. It may be wider than a membership row: conversation admits a workspace member to a public conversation. Every caller of that dimension gets the same answer, so an HTTP route and a realtime channel (ADR 0009 A8) cannot disagree. A membership dimension is a row-id dimension: its spec lists is_valid_row_id in validators, as the built-in id dimensions do (SCP-4). The check keeps the MembershipCheck signature, (session, *, account_id, container_id) -> bool. A route that needs the membership row (for a role) loads it in its context dependency. Returning the row from the check later would break every custom check; a separate, optional lookup registered beside it would not.
    • The envelope comes first. The request boundary builds the envelope: resolvers give its scope and principal, and each selector (SCP-3) is resolved to a row in the scope and added with envelope.extend(ScopeClass, **selectors). Containment, such as a workspace belonging to the request's tenant, is checked here (the place stage, AUZ-12), not in the constraint list. The constraints then run on that envelope. MembershipConstraint(dimension) reads the container's id from envelope.scope, the caller from envelope.principal and the check from the registry, and takes the session as an argument (evaluate(envelope, *, session)). Nothing reads a dimension string, and nothing writes a result back onto the envelope.
    • The operation lists its memberships in its profile's constraints, in container order (tenant, workspace, conversation) and before its role and permission constraints; the evaluator stops at the first denial. A dimension that is None on the scope skips its check (SCP-2). A membership follows the profile's enforcement level like every other grant check (AUZ-12), so a profile that lists one is enforce; a constraint not ready to enforce waits in a profile of its own.
    • Opting out is explicit. An endpoint that admits non-members names an operation whose profile leaves that membership out: accepting a workspace invite lists tenant membership only. An endpoint that reads no scoped data takes no envelope dependency. Which router a route sits on never decides it.
    • One mechanism wherever there is a request. The envelope dependency, the guards (SCP-6), realtime subscriptions and code that runs inside a request (an agent tool holding the request's envelope) decide through the same evaluator: ConstraintEvaluator.for_operation(...) and permits(envelope, session=...). The envelope dependency takes get_session once (API-7); no layer threads a check or a session further. A role source that counts a role only for members reads the check from the registry rather than taking it as an argument.
    • Background work runs no membership check. A job, a worker or an eventbus handler has no envelope (SCP-5): access was decided by the request that queued the work, and the job acts on a row's placement. What happens to queued work when a membership ends is decided by the code that ends it, not by the worker. Work that acts on a person's behalf (sending a message as them) needs its own design and is not covered here.

    Where each part lives:

    Layer Membership work
    Module import The owning module registers its dimension's MembershipCheck.
    Host startup Replaces a check, only to state a choice (replace=True).
    Dependency builder (mount time) Validates wiring: every MembershipConstraint a profile lists has a registered check whose signature binds; otherwise a startup error.
    Envelope dependency (per request, one per operation) Builds the envelope, resolves and extends its selectors, checks containment, runs the evaluator, maps the decision to HTTP, returns the envelope.
    Router Nothing. It may attach an envelope dependency router-wide when every route shares the operation.
    Endpoint Never checks. A membership row it needs (for a role) comes from an access-checked context dependency (API-1); a missing row means no role, not "not a member".
    Service Checks the accounts a request names (a share target, a new group member) with an injected MembershipCheck, and raises a domain error that the router answers with 404 (ERR-1).
    Action Holds the membership query only (SVC-2).

    The envelope dependency answers a missing principal with 401, a failed containment check or unknown selector with 404, and a denied membership with 403.
