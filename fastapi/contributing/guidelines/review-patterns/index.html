    Review patterns¶

    What automated reviewers (mainly Copilot) and human reviewers keep finding, and a self-review pass that catches it before the pull request opens. Use it with Reviewing pull requests (REV): that page says how to triage findings, this one says what to look for first.

    Where the findings come from¶

    The categories below were read off the inline review comments of the longest review cycles so far: #229 (243 comments), #243 (101), #255 (66), #252 (35),

    248 (19) and #244 (8), then checked against the review of #306. A keyword¶

    count over those comments is a rough guide only (a comment can match several categories):

    Pull request Dominant categories
    #229 tenancy migration edge values (NULL, sentinels), dependency and version pins, schema and migration, races
    #243 structured ingestion races and stale snapshots, edge values, input validation, test quality
    #252 ingestion lifecycle races (unlocked queue, dedupe), schema, error handling
    #255 schema setup schema and migration, over-broad guarantees in docs, test quality
    #244 after-commit work transaction and event ordering
    #306 authz privilege and scope mix-ups, races, NULL sentinels, Python floor, immutable identity

    Reviews also arrive in waves. Each push can trigger a new pass that finds new instances of the same class, which is why one pull request collects dozens of rounds. The cure is to remove the class (RVP-2), not to answer each instance.

    Categories¶

    Category Typical finding Rules
    Races check-then-insert, stale snapshot after slow work, deduped job swallows an update, unlocked queue CNC-1–6, CNC-11
    Transaction contract commit inside a building block, savepoint on SQLite, early return leaves a lock, event after a closed session CNC-7, CNC-8, SVC-4, SVC-10
    Edge values NULL/zero sentinel collisions, blank or oversized strings, naive datetimes, int() on untrusted text EDG-1–3
    Unchecked runtime values a typo in a Literal takes the weak branch, unknown enum falls through EDG-5
    Authorization tier or owner mix-up, a bare key compared across tiers, missing tenant defaults, bypass through a raw action AUZ-1–11, SCP-2, SCP-3
    Schema and constraints missing CHECK or unique index, un-migrated database, rule only in the service EDG-7, EDG-8, DEP
    Compatibility 3.11+ API, tag vs dev pins, optional extra imported at module scope EDG-4, DEP, ARC-2
    Docs and comments claims broader than the code ("every path", "never"), stale text, README disagrees with behaviour CNC-10, STY-3, MOD-8
    Tests test cannot fail, double drifted from the code path, asserts the wrong thing TST-6, TST-7
    Error handling broad except hides validation as "exists", wrong exception type, swallowed failure CNC-2, CNC-3

    Self-review before opening the pull request¶

    RVP-1 · Walk the categories on your own diff¶

    For each changed write path, ask:

    1. Two at once? If two processes run this at the same moment, what does the second one see, and what error does it get? (CNC-1–4)
    2. Slow step in the middle? Is anything checked before a slow call and trusted after it? (CNC-5, CNC-6)
    3. Who commits? Does the function honour its commit contract on every return path, including the early ones? (CNC-7)
    4. Edges of every input. NULL, 0, negative, empty, whitespace, 256 characters, a past timestamp, a non-numeric id, an unknown enum value. (EDG-1–3, EDG-5)
    5. Missing context. What happens with no tenant, no workspace, no account? It denies. (EDG-6, AUZ-8)
    6. Can a row written another way slip through? Is the rule enforced on read as well as on write, and in the database where a table can express it? (EDG-7, AUZ-2)
    7. Python 3.10. Any import or call that needs 3.11+? (EDG-4)
    8. Claims. Does a docstring, README or docs page promise more than the code enforces? (CNC-10)
    9. Tests. Is there a test for the serial case, the lost race (CNC-11), each edge value, and the denial path? Does the regression test fail first? (TST-6)
    10. Simpler? Could the same behaviour be done with less: fewer parameters, types or layers? What can be removed without losing something required? (AGT-12)
    11. Understandable? Would a new reader know what each new name is for? Does it follow the existing convention for that kind of thing? (AGT-13)

    RVP-2 · Sweep for the class before you push a fix¶

    When a reviewer finds one instance, search the module and its neighbours for the same pattern (grep for the call, the sentinel, the except) and fix them together, with a test per instance. Fixing only the cited line guarantees another round (REV-4).

    RVP-3 · Treat a finding as a claim to check, not a fact¶

    Automated findings are sometimes right about a symptom and wrong about the cause, or wrong outright (for example, claiming a test builds a row the schema forbids when the test builds a valid one). Read the code and run the case before changing anything (REV-2). When a finding is wrong, reply with the evidence. If the code is likely to be misread again, add a one-line docstring or comment that states the intent (STY-2), so it is not flagged on the next pass.

    RVP-4 · When there is a pile of findings, list them first¶

    For a long list, validate each against the code, group them by root cause, and propose one design per group before implementing. Report each as real, real but intended, or wrong, with the reason. Patching them one by one produces inconsistent fixes (CNC-2 and CNC-3 are an example: one shape for every lost-race path).

    RVP-5 · Prefer closing a class over answering a thread¶

    A recurring finding is a missing primitive. Add the helper, the constraint or the single decision function (is_effective_assignment, emit_deferred, ensure_*) and route every caller through it, instead of patching callers (ARC-6, REV-4).

    RVP-6 · Record what was learned¶

    When a review settles a convention or reveals a new class, add or amend the rule on these pages in the same pull request (REV-6), and add the failure shape to Known pitfalls if it cost time.

    RVP-7 · Review the fix, not only the change¶

    A fix is new code, and fixes to review comments draw their own comments. Before pushing one, run the RVP-1 pass (or /code-review) on the fix's own diff:

    • Walk each changed line for its failure scenario, and check the callers of any changed signature and whatever the fix moves or removes.
    • Confirm the new test fails without the fix (TST-6), and that any check you rely on can fail: a scan that visits zero files, or a script that ignores collection errors, passes for the wrong reason.
    • Sweep for the class the comment names, not the cited line (RVP-2).

    Why: on #306 each round of fixes brought a new round of comments, mostly about gaps the fix itself introduced: a per-row refresh that became O(N) in a batch, a check that ran after the commit, a payload value the event contract did not allow.
