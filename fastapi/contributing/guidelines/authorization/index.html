    Authorization¶

    Rules for code that grants, checks or guards access, written from the review of msflib-authz (#306). They apply to modules/authz, to the guards in modules/auth, and to any module that protects an endpoint. The module's own page (msflib-authz, added with #306) has the tables and examples; these rules say what to preserve when changing it. AUZ-12 places every check in the four stages of the access stack.

    AUZ-1 · Keep tier, owner and reach apart¶

    A role has three separate facts, and each lives in a different column (see Three questions about a role):

    Fact Question Stored on
    tier what level of authority does it grant? Role.tier
    owner who defined it, and who may use it? Role.tenant_id, Role.workspace_id
    reach where does this one grant apply? RoleAssignment.tenant_id, RoleAssignment.workspace_id

    NULL means "shared, no owner" on a role and "no tenant or workspace here" on an assignment. Never compare a role_* id with an assignment_* or request id as if they were the same thing; the names in the code (role_tenant_id, assignment_tenant_id) say which is which. Don't rename the columns to hide the distinction; document it.

    AUZ-2 · One rule decides whether an assignment can grant authority¶

    (The combinations are tabulated under Valid and invalid combinations.)

    is_effective_assignment (tier shape, the role's owner scope, expiry) is the only definition. Every read path (has_permission, get_role_keys_for) reaches it through one internal step. Do not add a resolution query that loads assignments another way, or a second copy of the rule.

    Why: every round of review found another read path that skipped one of the three checks.

    AUZ-3 · Compare roles by tier-qualified key¶

    Use RoleKey(tier, key). A bare key cannot tell the seeded tenant admin from the workspace admin. ROLE_REGISTRY takes RoleKey only (a bare string is a TypeError), and a legacy admin mirrored by a backfill is a tenant-tier role that never satisfies a platform RoleKey.

    AUZ-4 · Authority comes from the tier, never from NULL ids¶

    A platform role is platform-wide because its tier says so. NULL scope ids on an assignment of a tenant or workspace role are invalid and grant nothing. Enforce shape in the service on write, ignore bad rows on read (EDG-7), and add database CHECKs for everything a single table can express.

    AUZ-5 · Two ways to guard a route; authz does not leak into auth¶

    msflib-auth guards (RoleCheck, WorkspaceRoleCheck) compare a role attribute and are supported as the simple way. msflib-authz guards read assignments: the guard(key, tier=...) from get_authz_dependencies, by permission key, with role_registry=ROLE_REGISTRY to accept registered roles too. Pick one way per route. auth must not import authz, and authz must not import auth; identity arrives as injected callables.

    Name permission keys <module>.<action>, register them at import time, and choose tenant_cascade deliberately: True lets a tenant-tier role grant the permission inside any workspace of its tenant. Register roles for a key as RoleKey(tier, key), never a bare string.

    AUZ-6 · Write through RoleService; actions skip validation¶

    Actions are plain data access. A row created through one is checked by nobody, so do it only in tests that need an invalid row. Actions take the client schemas only, so scope and actor reach a row only through an explicit update=. In application code use create_role, ensure_role, grant, ensure_assignment and revoke.

    AUZ-7 · Authz services commit their own unit of work¶

    Every public authz service method is one closed unit of work (SVC-4): its writes run in savepoints, it commits once at the end, and its events fire on that commit. A method that writes several rows commits once for the whole batch (RoleService.ensure_roles, bundle_permissions, sync_legacy_assignments; GroupService.delete_group).

    • A method that other methods compose is split into a private step (_grant, _revoke) that does not commit and a public method that calls the step and commits. Only methods inside the authz package call the private steps.
    • The documented composition parameters are commit=True on AccessService.grant, AccessService.revoke_resources, ResourceSharing.share and ResourceSharing.revoke_all. The drivelink create-with-initial-shares and delete flows pass commit=False, so the node and its grants land in one commit and a failing step leaves neither. The role and group services have no such parameter.
    • Anything else that needs authz writes joined to its own goes through the same shape: a named caller, a documented parameter, a test that a failure leaves nothing behind.

    AUZ-8 · Deny by default¶

    Deny on a missing tenant when a tenant dependency is wired, an unknown tier, an unregistered permission key, a workspace of another tenant, and an expired assignment. Defaults (the default tenant) apply only when no dependency is configured.

    AUZ-9 · Legacy support is transitional¶

    (See Legacy roles.)

    The authz guards ignore Account.role and User.type. The two backfills mirror them into legacy_backfill assignments so a route can move from auth to authz without losing access, and they exist until assignments replace the attributes. Do not extend them. The two sources are independent: revoking an assignment does not change the attribute. Backfills take the complete set and revoke what it no longer implies; a partial list revokes too much.

    AUZ-10 · Rule changes update the docs tables¶

    The valid and invalid combinations table on the authz module page is checked against the code. Change a rule, change the table, and add the case to both the write test (grant rejects it) and the read test (a raw row that breaks it grants nothing).

    AUZ-11 · Reach and actor are parameters, not fields of *Create¶

    RoleCreate and RoleAssignmentCreate hold only what a client may send. The owner, reach, grantor and system flag are decided by the server and go to the service as owner=RoleOwner(...), reach=RoleAssignmentReach(...), granted_by_account_id and created_by_account_id (MDL-11). Build them in the endpoint from the request context, never from the body. A test asserts that the client schemas declare none of those fields.

    AUZ-12 · Each check belongs to one stage of the access stack¶

    A request passes four stages, in order. Each stage answers one question and fails one way, and no stage answers another stage's question.

    Stage Question On failure Policy
    1. Identity Who is calling? 401 no
    2. Place Does the place the request names exist, and do its parts belong together? 404 no
    3. Grant Does the caller hold a grant whose reach covers this place, at the level the operation needs? 403 yes
    4. Filter Which rows does the request see? fewer rows, never an error no

    Stages 1 and 2 build the envelope (SCP-4): identity gives envelope.principal and the place gives envelope.scope. Stage 3 decides on the envelope. Stage 4 receives it and filters on envelope.scope.

    • Only stage 3 is policy. An enforcement level (log-only, shadow, enforce) applies to stage 3 alone; stages 1, 2 and 4 always hold. A check that must never be switched off does not go in a constraint list.
    • Every grant is checked at stage 3. Membership, roles, permissions and resource access are all grants (SCP-5). Membership reaches a whole container, so it runs first, but it is checked the same way as the others.
    • 404 hides, 403 refuses. A place that does not exist, or a workspace of another tenant, is 404 at stage 2, so a caller cannot probe for another tenant's ids. Within a place the caller can see, a missing grant is 403.
    • A filter never decides access. An action filters on the scope it is given and checks no grant (SVC-2); an empty result is not a denial.
    • A third party's grant is stage 3 in a service. When a request names another account (a share target, a new group member), the service checks it with an injected MembershipCheck and raises a domain error that the router answers with 404 (ERR-1).
    • Background work skips stages 1 to 3. A job or event handler has no request: the request that queued it was allowed, and the job filters by the placement of the row it acts on (SCP-5).

    Where each control sits:

    Stage Control Owner
    1 The host's get_current_account; get_scope_dependencies puts a PrincipalContext (int account_id) on the envelope and answers 401 without one host app, core
    1 Realtime stream ticket (planned, ADR 0009 A8) realtime
    2 get_current_tenant (the default tenant when the app has no tenancy) tenancy
    2 get_current_workspace by slug, and the check that the workspace belongs to the request's tenant workspaces, core
    2 Id dimensions hold row ids (is_valid_row_id), checked when the envelope is built (SCP-4) core
    2 Checks on the scope's own values, such as DimensionMatchConstraint (moving here from the constraint list, ADR 0009 A9) core
    2 Selectors such as conversation_id resolve to a row in this scope before envelope.extend adds them (SCP-3) the selector's module
    3 MembershipConstraint with the container's MembershipCheck (is_workspace_member, tenancy's check, or allow_any_member) core; the check from the container's module
    3 Route guard: RoleConstraint with a RoleSource (auth attributes or authz assignments) and PermissionConstraint with the authz RoleService resolver, through build_guard or authz guard(key, tier=) core, authz
    3 RoleCheck, WorkspaceRoleCheck (AUZ-5) auth
    3 ResourceAccess rows through AccessService, for one resource; share links (planned, #367) authz
    3 ChannelConstraint and other constraints an operation's profile lists, such as ai_api's evaluate_scope_constraints core, modules
    4 Actions filter on envelope.scope; workspace_id=None is the workspace-less bucket (SCP-2) module actions
    4 Knowledge scoped_statement, documents list_for_scope, and PlacementReader (replaced RowScope in #413) knowledge, documents, core
    4 DimensionCompiler sinks: vector-store metadata filters, memory namespaces core, ai_core
    4 Reach filtering in search (planned, #403) knowledge, ai_core

    Not yet in line with this rule (ADR 0009 A9 decides each):

    • get_scope_dependencies answers a request with no tenant with 403. It is a stage 2 failure, so it becomes 404, as a request that needs a workspace and resolves none already is.
    • get_member_account_dependency runs the stage 2 workspace check and the stage 3 membership check together. It is deprecated in 0.3.0 and removed in 0.4.0; msflib/fastapi#424 brings build_envelope_dependency as the replacement. Until then a membership is checked outside the evaluator, so it ignores the profile's enforcement level.
    • DimensionMatchConstraint checks the scope's values, a stage 2 question, from the constraint list, so a log-only profile switches it off. It is removed in msflib/fastapi#424 (no current users outside tests).
    • Some operation profiles explicitly opt into log-only as a rollout exception (ai_api's profiles, workspaces' profiles), so their stage 3 grant constraints log rather than reject. log-only and shadow are valid explicit choices with a startup warning; whether these modules should move to enforce is undecided (msflib/fastapi#270).
