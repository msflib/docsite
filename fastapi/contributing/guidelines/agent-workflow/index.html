    Working as an agent¶

    These rules apply to any coding agent working in this repository. Most also apply to people.

    AGT-1 · Read before writing¶

    Read AGENTS.md and the guideline pages that cover the area you are changing. Look at how existing modules solve the same problem before inventing a new pattern, and name the reference you followed.

    AGT-2 · Present a plan before architecture-level changes¶

    When a change redistributes responsibility across files or layers (where checks live, how layers call each other, module boundaries), stop after the investigation and present the plan: files touched, what changes in each, what stays. Wait for an explicit go-ahead. An answer to a narrower question earlier in the conversation doesn't approve the whole plan.

    Straightforward bug fixes with an obvious, local resolution don't need this.

    AGT-3 · Ask when the decision belongs to the maintainer¶

    Ask before choosing compatibility shim or clean break (STY-4), before refactors with a large blast radius, and before anything outward-facing (pushing, opening or commenting on PRs and issues).

    AGT-4 · Check rationale against the code¶

    Before accepting a docstring or comment's claim about why something is designed a certain way, grep for real consumers. "Kept separate for architectural reasons" can be a leftover that was never reconciled.

    AGT-5 · Validate narrowly and report faithfully¶

    Run the narrowest check that proves the change (TST-1). Report failures with their full output. Don't describe work as done or verified unless it was.

    AGT-6 · Where plans live¶

    • work/ is a private, gitignored scratch area for planning notes. Nothing there is shared, so never cite it as a source in committed code or docs.
    • Architecture plans meant to be shared become GitHub tracking issues.
    • Content that must be versioned moves from work/ into a tracked location (for example these pages).

    AGT-7 · Branching and merges¶

    Branch from dev; target dev. Write PR descriptions from the org template (REV-7). When syncing a long-lived branch with dev, first diff the branch's own commit range to find which conflicted files it actually touched; files it never changed can take dev's side.

    AGT-8 · Stay in scope¶

    Follow STY-6. When you notice an unrelated issue, report it instead of fixing it.
