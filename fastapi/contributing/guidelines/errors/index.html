    Errors and exceptions¶

    Code below the HTTP layer is also called from CLIs, workers, seed scripts and tests, so it reports problems in Python terms. The request layer turns them into HTTP responses.

    ERR-1 · HTTPException is raised only at the request layer¶

    fastapi.HTTPException (and fastapi.status codes) may appear only in request endpoint functions in router.py and in FastAPI dependencies in deps.py. Services, service classes, actions, models, utilities and integrations must not import or raise it.

    Why: an HTTPException escaping a CLI or worker is a stack trace carrying an HTTP status nobody reads, and callers that want to react must inspect status_code instead of catching a type.

    ERR-2 · Prefer a built-in exception when it says what happened¶

    Use Python's own exceptions where their meaning is exact, and don't wrap them for the sake of it:

    Situation Raise
    Bad argument value ValueError
    Wrong argument type TypeError
    Missing key or id the caller looked up LookupError (KeyError for mappings)
    Caller may not do this PermissionError
    External call timed out TimeoutError

    A built-in is not mapped to a status automatically, because a stray ValueError is as likely to be a bug as a client mistake. The router catches the ones it expects (ERR-4). When the API should answer the problem with a specific status without a catch in every endpoint, use the matching core class instead (PermissionDeniedError rather than PermissionError, NotFoundError rather than LookupError; ERR-3).

    ERR-3 · Shared domain exceptions live in core¶

    When the caller needs to tell the problem apart and several modules hit it, use the exception from msflib.core.exceptions instead of redefining it per module. All derive from BaseServiceError, the base for anything services, actions and utilities raise; name new ones <Problem>Error (SDC-4).

    Exception Meaning Status
    NotFoundError the requested entity does not exist or is out of scope 404
    ConflictError uniqueness or state conflict 409
    InvalidInputError input breaks a domain rule the schema cannot express 422
    UnsafeInputError input rejected for safety (path escape, non-https URL) 400
    PayloadTooLargeError input over an allowed size 413
    UnsupportedContentError content type not accepted 415
    PermissionDeniedError authenticated but not allowed 403
    AuthenticationError credentials missing or wrong 401
    NotSupportedError not implemented for this configuration 501
    ServiceUnavailableError a backing service is not configured or reachable 503
    ExternalServiceError (and any unmapped BaseServiceError) an outside call or backend failed 500

    UnsafeInputError, PayloadTooLargeError and UnsupportedContentError are subclasses of InvalidInputError, and ServiceUnavailableError of ExternalServiceError, so catching the parent also catches them.

    A module defines its own exception only when it carries data a caller needs or must be told apart, and derives it from the matching core class (class StorageError(ExternalServiceError) in msflib.utils.uploads). Keep exceptions free of HTTP vocabulary: no status_code, no detail; carry ids and field names as attributes. Pick the core class whose status matches what the API already returns; don't change a response code as a side effect.

    ERR-4 · One place maps exceptions to responses¶

    msflib.api.errors.STATUS_BY_ERROR holds the status for each core class, and the nearest mapped parent wins. A host app installs it once:

    from msflib.api import register_exception_handlers

register_exception_handlers(app)

    The handler answers {"detail": str(error)} with the mapped status. A router that must not depend on the host (or maps a module exception, a built-in or a different status) catches it in the endpoint or dependency and raises HTTPException there, as account does for IncorrectPasswordError. Services never decide a status.

    Test apps that exercise error paths call register_exception_handlers(app) in their app fixture.

    Request-shape validation stays with the schema (API-6) and raises there.

    ERR-5 · Don't swallow, don't retype¶

    • Never except Exception and return None or a default; catch the specific class you can handle.
    • Re-raise with context: raise NotFoundError(...) from exc.
    • Workers classify failures with msflib.core.errors.is_terminal_ingestion_error instead of each inventing a retry rule.

    Background workers¶

    msflib.core.errors.is_terminal_ingestion_error treats the client-side core errors (InvalidInputError and subclasses, NotFoundError, ConflictError, PermissionDeniedError, AuthenticationError, NotSupportedError) as terminal and ExternalServiceError as retryable. Raise the class that matches, and the worker needs no special case.

    Known gaps¶

    modules/conversation/.../integrations/ai_bridge.py builds FastAPI dependencies and raises HTTPException in them. They are dependencies in the ERR-1 sense but live outside a deps.py; they move there, or raise domain exceptions, when that module is next reworked.

    core/errors.py still imports HTTPException to classify failures raised by providers that predate ERR-1 (is_terminal_ingestion_error). It only inspects the exception and never raises one; the import goes once those providers raise domain exceptions.

    Open point

    deps.py dependencies (401/403 guards, tenant resolution) still raise HTTPException, as ERR-1 allows. Whether they should move to the same handler is undecided.
