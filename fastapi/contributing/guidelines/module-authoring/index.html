    Module authoring¶

    How to scaffold, install and register a module is in Adding a module. This page covers how the code inside msflib/<name>/ is organised.

    MOD-1 · Use the standard package layout¶

    msflib/<name>/
  __init__.py         # empty, or lazy __getattr__ (MOD-2)
  config.py           # <Name>Settings(ModuleSettingsBase), ClassVar namespace
  models/             # one file per entity: table + its Create/Update/Read schemas
  actions.py          # all database access (SVC-1); a package if it grows
  services/           # business logic (SVC-*)
  eventbus/           # EventName enum + typed event contracts (MOD-5)
  contracts/          # Protocols and type aliases for cross-module structural typing
  deps.py             # request-scoped FastAPI dependencies (API-2), if needed
  router.py           # only if the module exposes HTTP endpoints
  scope_profiles.py   # if the module registers scope profiles (SCP-4)
  integrations/       # optional integrations with other modules (DEP-2)
  tests/
  <special>/          # registries, compilers, planners, parsers, adapters (MOD-4)

    Reference: modules/conversation/msflib/conversation/, modules/documents/msflib/documents/.

    MOD-2 · __init__.py never imports eagerly¶

    Keep it empty, or use a lazy __getattr__ map with absolute msflib.<name>.… paths:

    def __getattr__(name: str) -> Any:
    mapping = {"FooAction": ("msflib.foo.actions", "FooAction")}
    if name not in mapping:
        raise AttributeError(f"module {__name__!r} has no attribute {name!r}")
    module_name, attr_name = mapping[name]
    return getattr(import_module(module_name), attr_name)

    An unknown name must raise AttributeError, not KeyError, so hasattr() and failing from msflib.foo import x imports behave normally. Reference: documents/__init__.py.

    Why: the namespace package is importable under several sys.path entries. Eager model imports register SQLModel tables twice ("Table already defined") and pull optional dependencies in at import time.

    MOD-3 · Business logic lives in services/ (plural)¶

    Every module, and the module template, uses services/. Modules that used to have service/ keep it as a deprecated alias package that re-exports services/ and warns on import. Don't add code to a service/ alias or import from it; the aliases will be removed in a future minor release.

    MOD-4 · Special logic gets its own package¶

    Registries, compilers, planners, parsers and adapters, meaning logic that is neither CRUD nor orchestration, go in dedicated packages (documents/adapters/, ai_core/services/chunking/, knowledge/planner/). New registries follow the ChunkingRegistry shape: register, resolve, list, with capability records.

    Don't create a package or module for a one-line helper. A helper reused at least three times within one file may become a private function in that file.

    MOD-5 · Eventbus layout¶

    • eventbus/events.py holds EventName(BaseEnum), typed EventOptions contracts and an EVENT_CONTRACTS map.
    • Emit with msflib.eventbus.emitter.emit_optional(EventName.X, subject, options).
    • Don't re-emit what ModelAction lifecycle events already cover. Module events are for domain moments (knowledge-fragment-ingested, account-created-pre-email).
    • Events tied to an uncommitted write use emit_after_commit (SVC-10).

    MOD-6 · Settings are scoped¶

    config.py defines <Name>Settings(ModuleSettingsBase) with a ClassVar namespace. Classes that need settings receive them in __init__ and call settings.scope("<NAMESPACE>").

    MOD-7 · Background pipelines register with msflib.ingestion¶

    Any fetch → transform → persist background flow registers a pipeline_kind with msflib.ingestion instead of building its own queue. Follow modules/ingestion/README.md ("Adding a new pipeline kind" and "Wiring into a host app"). Examples: msflib.documents.services.pipeline (simple stage singleton) and msflib.knowledge.integrations.pipeline (stage built by a factory because it needs a constructed KnowledgeEngine).

    MOD-8 · Keep the module's docs current¶

    When capabilities change, update the module README.md (what it owns, layout, usage snippets, boundaries, status) and its page under docs/modules/. See Writing docs.
