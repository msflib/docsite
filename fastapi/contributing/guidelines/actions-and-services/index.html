    Actions and services¶

    Action classes¶

    SVC-1 · All database access goes through ModelAction¶

    • Every table has an action class extending msflib.actions.ModelAction[Model, Create, Update].
    • Mutations go through super().create/update/delete (with decorator= and commit=) so ModelBase lifecycle events fire. Never session.add() a row from a service or router.
    • Services use an existing action instead of querying the session directly.

    Known gap

    auth/router.py sets last_login_date on login with session.add() and session.commit() directly. Don't copy it; it needs its own change to go through the account action.

    SVC-2 · Actions hold only database concerns¶

    Keep in the action: query construction (filters, ordering, joins) and write concurrency mechanics (nested transactions, IntegrityError fallbacks). Move domain policy (retry backoff, state transitions) into a function in services/ and pass the result to update/create.

    Delete action methods that only reshape **filters into get_by_all or wrap self.update with a computed dict (mark_done); call the base method instead. Don't coerce types inside actions; shape the models and schemas so data arrives typed.

    SVC-3 · Multi-dimension scoped queries take the typed scope object¶

    A query filtering on two or more scope dimensions takes the module's scope contract (a TenantScope subclass such as ConversationScope or KnowledgeScope) as one parameter, not a growing list of scalars. The request boundary builds it once (SCP-4) and each layer passes it on unchanged; only the action unpacks it into column filters. A single scalar such as tenant_id is fine when only one dimension applies.

    Services¶

    SVC-4 · Each service function is one closed unit of work¶

    A service function commits itself and takes no commit: bool parameter.

    An exception needs a named, current caller that composes it with another call in one transaction, documented in the function's docstring. Before adding commit=False anywhere, grep for callers that pass it; an unused commit parameter should be removed.

    Documented exceptions to follow: KnowledgeEngine.ingest (commit=False joins a larger caller transaction, deferring its post-commit work) and IngestionDispatchService.enqueue_and_dispatch_created (commit=False with dispatch_after_commit for a caller that owns the outer transaction). Don't flag a documented commit parameter like these as a violation.

    Under review

    documents/services/uploads.py upload_file() keeps a commit parameter whose only caller passes commit=True.

    SVC-5 · Compose multi-row writes on the action, or inside one service method¶

    • Several rows that form one database concern (create a conversation with its owner membership and event) are one action method that uses commit=False internally and commits once.
    • When a service must combine actions atomically (get-or-create a thread, then post a reply), keep both calls in that one service method: the first call uses commit=False, the second commits, and a failure path calls session.rollback() and re-raises. Never compose transactions in the router.
    • A cross-module unit of work (blob storage + a documents action + an ingestion dispatch) is the legitimate case for a service-level composition.

    SVC-6 · Services with dependencies are classes with constructor injection¶

    A service that needs actions or settings is a class that receives them in __init__ (defaulting to new instances). session and per-call data (scope, participant, rows) stay method arguments. Pure predicates over loaded rows stay plain functions. Reference: conversation/services/, ai_core/services/ingestion_pipeline.py.

    Name a constructor argument for what it holds: a service taking already-scoped ConversationSettings uses conversation_settings=, not settings=, which elsewhere means the raw host settings.

    SVC-7 · Resolve default collaborators lazily when they form a cycle¶

    If default-constructing a collaborator in __init__ would construct back to the current class (ConversationAction → MemberAction → MessageAction), store None and resolve it on first use inside the method.

    SVC-8 · Pass the boundary schema through unchanged¶

    A Create/Update built at the boundary flows to the action as the same object (data: MessageCreate). Don't unpack it into scalar parameters in the service and rebuild it in the action. Pass service-computed additions alongside it via update= or data.model_copy(update=...).

    • Single-field operations (mark_read(up_to_message_id)) keep a plain scalar.
    • For an Update shared by several operations, project one operation's fields with data.model_dump(exclude_unset=True, include={...}), not per-field if x is not None blocks.

    SVC-9 · Return related rows you just created¶

    A create method that also inserts a related row may return tuple[Model, Related] (or Related | None) so callers don't re-query it. Retrofitting this onto existing call sites is a larger change; confirm before starting.

    Events and transactions¶

    SVC-10 · Defer events until commit¶

    When a write uses commit=False, emit its event with msflib.actions.emit_after_commit(session, event, instance, payload) so listeners never see uncommitted state. Don't hand-roll paired sqlalchemy.event.listen(..., once=True) callbacks.

    Listeners receive (instance, payload), not a session. Payloads carry public ids and scope values so listeners can act without re-querying.

    Where checks live¶

    SVC-11 · Put each check in the layer that owns it¶

    Check Where
    Access decisions, including "this membership belongs to this conversation" access predicates (services/access.py)
    Another entity belongs to the conversation (message, thread, resource) inline in the service
    Consistency between rows the action already has in memory inline in the action, only when no extra query is needed

    Don't inject an extra action just to re-check something the caller already validated. Don't create a shared module for a single comparison.
