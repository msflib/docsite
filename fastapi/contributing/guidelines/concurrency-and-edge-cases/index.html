    Concurrency and edge cases¶

    Two classes of finding recur in every long review: a write that is only safe when one process runs at a time, and a value at the edge of its domain (NULL, zero, blank, naive time, an unknown enum). Both pass single-process tests, so reviewers keep finding new instances after each round. Check these before opening the pull request (RVP-1).

    Examples cite the review history of #229, #243, #244, #252 and #255, and the authz module (#306), where each rule was applied.

    Races¶

    CNC-1 · A lookup before a write is not a guard¶

    get(...) followed by create(...) lets two writers both see "absent". Back every uniqueness rule with a unique index or constraint, and treat the lookup as a fast path and a source of a friendly error, not as the guarantee.

    Why: the loser surfaces as a raw IntegrityError at the worst moment, for example two workers seeding at startup.

    CNC-2 · A lost race raises the same error as the serial path¶

    Catch IntegrityError around the insert, re-read the row, and raise the domain error the pre-check raises (an ...ExistsError that subclasses ValueError). Re-raise the original error when the row is still absent, so a foreign-key or check violation is not reported as a duplicate.

    try:
    with atomic(session):
        row = self._action.create(session, data=data, commit=False)
except IntegrityError:
    if self._find(session, data) is not None:
        raise AssignmentExistsError(...) from None
    raise

    Why: callers handle one error, not two, and a test for the serial case covers the race.

    CNC-3 · Seed and startup paths use ensure_* (get-or-create)¶

    Anything that runs on every start, or from several processes, goes through an idempotent method (ensure_role, ensure_assignment). It returns the existing row unchanged, except where the method states a stricter contract (ensure_role(is_system=True) raises RoleExistsError when the existing role is not a system role). It catches only the specific "exists" error, so invalid data still raises.

    Why: catching ValueError broadly hides validation failures as "already exists".

    CNC-4 · An upsert retries the other branch when it loses¶

    An upsert reads, then updates or inserts. If the insert loses a race, re-read and update the winner's row; if it was already an update, re-raise. See AccessService.grant (#308).

    CNC-5 · Revalidate after slow work¶

    A check done before a slow step (an LLM call, a mapper, a network read, a queue wait) is a snapshot. Re-read and compare after the step, under the row lock or version check, and compare everything the result depends on (version and scope), not one field. If a newer version landed, discard the result.

    Why: "v2 passes the check, v3 finishes, v2 resumes and overwrites v3" was raised on #243 and #252.

    CNC-6 · A deduped job can swallow the update it was meant to carry¶

    If enqueue returns an existing in-flight job for the same key, the new payload is only processed if that job re-reads its source after the change. Either make the dedupe key change with the source (version bump), lock around the process-and-revalidate step, or make the job re-resolve the source before it finishes. Test the "update arrives while the job runs" ordering (#252).

    CNC-7 · Write inside a savepoint, never commit in a building block¶

    Service writes run inside atomic(session) (a savepoint), so a failure undoes only that write and the caller keeps its pending work. On a SQLite engine use the core helpers (enable_savepoints, begin_sqlite_transaction), or the savepoint can commit outside the caller's transaction (#243; pitfalls).

    An early-return branch (identical resubmission, existing row) still honours the method's commit contract: it must not leave a lock or an open transaction the caller believes is closed.

    CNC-8 · After-commit work outlives the call that scheduled it¶

    emit_deferred fires on the outermost commit. Do not hand listeners a session that the scheduling code closes on return, and do not assume async listeners finish before the request does (#244).

    CNC-9 · Process-wide caches hold committed values only¶

    A cache keyed on a database id (the default tenant id) is filled after commit and cleared on rollback. Registering a commit hook without a matching rollback hook caches ids that never existed (#229).

    CNC-10 · Claim only the guarantee the code enforces¶

    "Atomic", "idempotent", "rolls back on any failure" and "never" are claims a reviewer will test. Name the limit next to the claim: a savepoint does not undo a sibling's commit, an advisory lock held by a transaction ends with it, a migration that opts out of the transaction cannot roll back (#255).

    CNC-11 · Test a race by making the lookup miss once¶

    A test on one in-memory SQLite connection cannot race. Create the winner's row first, so the unique constraint is real, then patch the pre-check to return nothing on its first call and the real result afterwards. The insert now violates the constraint and the recovery path runs: assert the domain error (CNC-2) or the winner's row (CNC-3, CNC-4), and assert the lookup was called twice, which proves the recovery re-read ran. A test where no row exists only exercises the happy path. The test must fail without the fix (TST-6).

    def miss_once(real):
    calls = []

    def lookup(*args, **kwargs):
        calls.append(1)
        return None if len(calls) == 1 else real(*args, **kwargs)

    lookup.calls = calls  # assert len(lookup.calls) == 2 after the call under test
    return lookup

    Real concurrency (two sessions on Postgres) is not covered by this; say so in the pull request when it matters.

    Edge values¶

    EDG-1 · NULL in a unique key needs a sentinel outside the valid domain¶

    SQL treats NULLs as distinct, so a unique index over nullable scope columns does not enforce uniqueness. Coalesce NULL to a sentinel and make the sentinel impossible as a real value:

    • use -1 (as the knowledge identity indexes do), not 0, and
    • reject non-positive ids in validation and with a CHECK (id > 0) constraint, so no real id can equal the sentinel.

    Why: 0 and NULL collided in the authz identity indexes (#306).

    EDG-2 · Validate ids and strings at the boundary¶

    • Ids are positive integers; reject zero and negatives.
    • Strings that identify something are trimmed, non-blank and bounded by the column length (Field(min_length=1, max_length=255)). SQLite accepts a 500-character value that PostgreSQL rejects with a database error; MDL-12 says where the check lives.
    • Validate before casting: int(principal_id) on a non-numeric string raises ValueError mid-request.

    EDG-3 · Time is timezone-aware UTC¶

    Create "now" with datetime.now(timezone.utc). SQLite returns naive datetimes; treat them as UTC before comparing. An expires_at equal to now is expired. Reject a value that is already expired at write time rather than storing a row that never grants anything.

    EDG-4 · Stay inside the Python floor¶

    pyproject.toml declares Python >=3.10. Do not use 3.11+ APIs: datetime.UTC (use timezone.utc), enum.StrEnum, tomllib, ExceptionGroup, typing.Self, asyncio.TaskGroup. A single import of one makes the whole package fail to import on 3.10, and the module's tests fail at collection.

    EDG-5 · Literal and type hints are not runtime checks¶

    A misspelled tier, role kind or mode that falls through an if/else weakens a guard silently (tier="platfrom" became a tenant check). Coerce with the enum at construction (RoleTier(tier)) so a bad value fails when the dependency is built, not when a request arrives.

    EDG-6 · Missing context denies; defaults apply only when nothing is wired¶

    If a dependency that supplies the request's tenant is configured and returns nothing, deny. Fall back to the default tenant only when no such dependency exists. The same holds for an unregistered permission key, an unknown tier and an absent account.

    EDG-7 · Constraints that a database can express live in the database¶

    Put CHECK and unique constraints on the table, and validate the same rule in the service so the caller gets a message (EDG-2). A rule that spans two tables (a role's tier against its assignment's scope) cannot be a CHECK: enforce it in the service on write and ignore violating rows on read, so a row written any other way grants nothing.

    EDG-8 · Identity fields are immutable¶

    Fields that define what a row is (a role's key, tier and owner) are not in the Update schema. Changing them would reinterpret every row that references it. Create a new row and move the references.

    EDG-9 · Define what a repeated action does to a row in each lifecycle state¶

    A unique index plus an expiry means an expired row blocks a fresh grant. Decide and test each state: active (duplicate error), expired (renew), revoked (create).

    EDG-10 · Keep the bound parameters of one statement bounded¶

    Every value in an IN (...) list or a multi-row VALUES is a bound parameter, and a database caps how many one statement may carry: SQLite 999 on older builds (32,766 since 3.32), PostgreSQL tens of thousands depending on the driver. Past the cap the statement fails with a database error that the client sees as a 500, and tests with a handful of rows never get there.

    • Don't turn a collection that grows with the data (an account's groups, the children of a folder, a page of ids) into column.in_(python_list).
    • When the ids already live in a table, nest a subquery or join: RoleAssignment.principal_id.in_(select(...)). Reference: GroupMemberAction.build_group_subquery.
    • When the ids come from the caller, query in batches of at most 500 and merge the rows. Reference: AccessService.resolve_accesses and msflib.db.batching.BATCH_SIZE (500). Say in the docstring that the query count grows with the batches.
    • A collection that is small by construction (an ancestor chain, the members of an enum) may stay a plain IN list.
    • Test it with more ids than the limit's safe margin: record the parameter count per statement with a before_cursor_execute listener and assert it stays under the batch size, rather than depending on one engine's limit.

    Why: group-expanded role resolution built one IN list from every group a user belonged to (#307), and the bulk access lookup one from every resource id in a listing (#308); both were found in review, not by a test.
