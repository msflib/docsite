    msflib-auth¶

    Purpose¶

    msflib-auth issues access tokens and gives your host app the FastAPI dependencies that identify the caller. It covers password login, logout (token revocation), password recovery, optional Google OAuth, and two dependency factories: one that resolves the current account from a bearer token, and one that resolves the current workspace and the account's membership in it.

    It does not define your account or workspace models. You pass them in, typically the ones from msflib-account and msflib-workspaces.

    For the end-to-end picture of how a request becomes a scoped identity, see Scopes, tenancy and workspaces.

    Install¶

    [tool.poetry.dependencies]
msflib = { git = "https://github.com/msflib/fastapi.git", subdirectory = "core", rev = "core-v0.2.1" }
msflib-auth = { git = "https://github.com/msflib/fastapi.git", subdirectory = "modules/auth", rev = "auth-v0.2.2" }

    The package depends on authlib and itsdangerous. It imports no other MSFLib module, so it works with any SQLModel account model that has email, hashed_password and status columns.

    msflib/auth/__init__.py exports nothing. Import from the submodules: msflib.auth.deps, msflib.auth.router, msflib.auth.resolvers, msflib.auth.config, msflib.auth.eventbus.

    Wiring into a host app¶

    Build the dependency namespaces once at startup, then mount the router.

    from fastapi import FastAPI
from msflib.auth.deps import get_account_dependencies, get_user_dependencies
from msflib.scope import ROLE_LOOKUP_REGISTRY, no_workspace
from msflib.tenancy.deps import get_tenant_dependencies
from msflib.auth.resolvers import PathParameterResolver
from msflib.auth.router import router as auth_router
from msflib.workspaces import is_workspace_member

tenant_deps = get_tenant_dependencies(
    session_dep=get_session, tenancy_settings=settings.scope("TENANCY")
)
account_deps = get_account_dependencies(
    AccountModel=Account,
    oauth_token_url="/api/v1/auth/login",
    secret_key=settings.SECRET_KEY,
    session_dep=get_session,
    keystore_dep=get_keystore,
    get_current_tenant=tenant_deps.get_current_tenant,
    get_current_workspace=no_workspace,
)

# Only needed when your app has workspaces.
user_deps = get_user_dependencies(
    UserModel=User,
    WorkspaceModel=Workspace,
    session_dep=get_session,
    account_dependencies=account_deps,
    is_workspace_member=is_workspace_member,
    workspace_resolver=PathParameterResolver(),
)
ROLE_LOOKUP_REGISTRY.register(user_deps.role_lookup)
ROLE_LOOKUP_REGISTRY.lock()

app = FastAPI()
app.include_router(
    auth_router(
        get_session=get_session,
        get_keystore=get_keystore,
        get_current_account=account_deps.get_current_account,
        account_type=Account,
        account_read_type=AccountRead,
        settings=settings,
        prefix="/api/v1/auth",
    )
)

    What you supply:

    Argument Meaning
    session_dep / get_session A FastAPI dependency yielding a SQLModel Session.
    keystore_dep / get_keystore A dependency returning a StoreInterface (for example msflib.core.store.MapStore). Used to record revoked accounts.
    secret_key The key that signs and verifies JWTs. Use the same value as settings.SECRET_KEY; the router signs with the latter.
    settings Your settings object. The router reads the AUTH namespace from it and SECRET_KEY as a flat attribute (settings.SECRET_KEY).

    Known issue (#287)

    The router reads settings.SECRET_KEY from the top level of the settings object. With fully composed settings (core only under CORE, as in the quick-start layout) POST /auth/login and the password reset endpoints raise AttributeError, although get_account_dependencies(secret_key=settings.scope("CORE").SECRET_KEY) itself works. Mix CoreSettings into your settings class (class Settings(CoreSettings, SettingsBase), with the other modules still nested) so SECRET_KEY is a top-level attribute.

    get_account_dependencies also accepts active_statuses (default ["active", "online"]) and account_role_attr (default "role"). get_user_dependencies accepts user_role_attr (default "type"), current_workspace_attr (default "current_workspace_id") and workspace_resolver.

    Routes added by the router¶

    Route (under the prefix) Behaviour
    POST /login OAuth2 password form (username is the email). Returns access_token, expires, token_type, account and user. With a second factor it may answer 202 with a challenge and no token.
    POST /login/otp/request, POST /login/otp Login by code in place of the password. Return 403 unless ENABLE_OTP_LOGIN is true.
    POST /email-verification, POST /verify-email Email verification: send a code, then confirm it.
    POST /login/second-factor Only when the router is given second_factor. Exchanges a challenge token and a code for the access token.
    DELETE /logout Revokes every token issued so far for the caller's account.
    POST /password-recovery Emails a reset link and a short code. The answer is the same whether or not the email is registered.
    POST /verify-token Checks a reset token or a short code plus email. A wrong code counts as a guess.
    POST /reset-password Sets a new password from a valid reset token or code, once, and revokes the account's tokens.
    GET /google/login, POST /google/callback Google OAuth. Return 403 unless ENABLE_GOOGLE_OAUTH is true.

    The router takes optional hooks: access_token_claims_decorator(account, context) adds claims to the JWT, access_token_decorator(payload, context) rewrites the login response, send_reset_pwd_email_override replaces the recovery email sender, access_token_response_type replaces the Token response model, auth_payload_type validates extra data a client sends to the Google callback, and account_action replaces the action the router uses to look up accounts and record logins and password resets (see Subclassing actions). Because those writes go through the action, password resets fire the account's update-pre-commit and update-post-commit events. Logins fire those events only when the account model defines a last_login_date field (the update is skipped otherwise).

    Configuration¶

    Settings live in the AUTH namespace (msflib.auth.config.AuthSettings). Lifetimes and attempt limits must be at least 1, and the pauses and the lock wait at least 0; a lower value is refused when the settings load.

    Key Default Notes
    ACCESS_TOKEN_EXPIRE_MINUTES 30 Lifetime of tokens issued at login.
    EMAIL_RESET_TOKEN_EXPIRE_HOURS 48 Lifetime of the password reset link.
    PASSWORD_RESET_CODE_EXPIRE_MINUTES 15 Lifetime of the short code in the same email.
    PASSWORD_RESET_MAX_ATTEMPTS 5 Wrong codes allowed before the reset must be requested again.
    PASSWORD_RESET_MIN_INTERVAL_SECONDS 60 A second request for the same email inside this time sends nothing.
    OTP_CODE_EXPIRE_MINUTES 10 Lifetime of an email verification or login code.
    OTP_MAX_ATTEMPTS 5 Wrong codes allowed before a new one must be requested.
    OTP_MIN_INTERVAL_SECONDS 60 A second request for the same email and purpose inside this time sends nothing.
    ENABLE_OTP_LOGIN false Allows login with a code sent to the account's email.
    REQUIRE_EMAIL_VERIFICATION false Refuses login (403 "Email not verified") until the account's email is verified. Needs email_verification= on the router.
    SEND_VERIFICATION_ON_REGISTRATION false Sends the verification code when an account is registered. Needs register_event_hooks, and email_verification on the router (the router refuses to start without it).
    SECOND_FACTOR_CHALLENGE_EXPIRE_MINUTES 5 Time to enter the second-factor code after the password.
    SECOND_FACTOR_MAX_ATTEMPTS 5 Wrong second-factor codes allowed per challenge.
    EMAIL_LOCK_WAIT_SECONDS 5 How long a login, code or recovery request waits for an email that is being changed before answering 503.
    EMAIL_LOCK_HOLD_SECONDS 30 When the lock an email change takes frees itself if the update never finishes (for example, it was rolled back).
    PASSWORD_RESET_PATH /reset Appended to CORE.CLIENT_HOST in the reset email link.
    ENABLE_GOOGLE_OAUTH False Enables the Google routes.
    ALLOW_GOOGLE_OAUTH_SIGNUP False Create an account for an unknown Google email. Requires a listener for google-account-create.
    GOOGLE_OAUTH_CLIENT_ID, GOOGLE_OAUTH_CLIENT_SECRET empty Read when the router is built.
    GOOGLE_REDIRECT_URI empty Default redirect when the client does not send one.

    How you set these from the environment depends on how you compose settings:

    • Subclassed (class Settings(AuthSettings, CoreSettings, SettingsBase), as used by the repository's test site): use the flat field name, for example ACCESS_TOKEN_EXPIRE_MINUTES=60.
    • Composed style (AUTH: AuthSettings = AuthSettings() as a field): use the nested form, AUTH__ACCESS_TOKEN_EXPIRE_MINUTES=60. The flat names also work for every key in the table above.

    Either way, code reads values with settings.scope("AUTH").

    Behaviour may change (#280)

    The nested NS__KEY environment style only works for composed (field) settings, not for subclassed hosts. Use the flat field name with subclassed settings, as described above.

    Key concepts¶

    Account dependencies¶

    get_account_dependencies(...) returns a namespace with:

    Member Behaviour
    get_current_account Decodes the bearer token, rejects it with 401 if invalid or revoked, loads the account by email == token.sub, and 404s if it does not exist.
    get_current_account_or_none Same, but returns None when no token is sent. For endpoints that serve both anonymous and signed-in callers.
    get_current_active_account Also requires account.status in active_statuses; otherwise 401.
    get_current_active_superuser Also requires account.role == "root"; otherwise 403. This check is hard-coded and ignores account_role_attr (see the notice below).
    RoleCheck(roles) A callable class for dependencies=[Depends(RoleCheck([...]))]. Passes only when the account's role attribute is in roles; otherwise 403. An account without an id is a 401, and a request without a tenant is refused before any role is checked. It does not check the account's status; add Depends(get_current_active_account) to require an active account.

    Known issue (#272)

    get_current_active_superuser hard-codes account.role == "root" and ignores account_role_attr. If your role attribute or superuser role differs, require both get_current_active_account and RoleCheck([...]) with the roles you want. RoleCheck alone depends on get_current_account, so it also admits inactive accounts that have a matching role.

    RoleCheck is an exact membership test. RoleCheck(["admin"]) does not admit root; list every role you want to allow.

    RoleCheck and WorkspaceRoleCheck each resolve the request's envelope first, so a missing account (401), a missing tenant (404) or, for WorkspaceRoleCheck, a workspace of another tenant (404) is answered before any role or workspace user is looked at. Each check reads the caller's roles from the site's one role lookup when it decides (stage 3 of AUZ-12), whichever module provides it. A site that keeps roles as attributes registers auth's at startup, then locks the registry: ROLE_LOOKUP_REGISTRY.register(user_deps.role_lookup) and ROLE_LOOKUP_REGISTRY.lock() (from msflib.scope). account_deps.role_lookup reads the account's role (root as platform:root, any other as tenant:<role>), and user_deps.role_lookup reads it and the workspace user's type (workspace:<type>). A site with msflib-authz registers authz's role lookup instead (get_authz_dependencies(...).role_lookup, built with msflib.authz.deps.build_role_lookup), and these checks then read assignments. Nothing stamps roles on the envelope. Without a registered, locked role lookup, RoleCheck and WorkspaceRoleCheck raise ValueError when their route is declared, as every role check does; a lookup cleared after startup makes them deny with role_lookup_unregistered. Each check runs through msflib.scope.ConstraintEvaluator as a RoleConstraint on that envelope, so a decision is recorded with the request's tenant (and workspace, for WorkspaceRoleCheck) like any other scope decision. The checks run at core's guard.check profile level, which enforces; a host that re-registers that profile at shadow makes them record denials without refusing the request. get_user_dependencies reads role_lookup from the account_dependencies it is given, so pass the namespace get_account_dependencies returned; a hand-built one needs that member. The tenant comes from the get_current_tenant passed to get_account_dependencies; a site without tenancy passes the msflib.tenancy resolver, which falls back to the default tenant.

    Roles for the guard¶

    build_role_lookup (in msflib.auth.roles) returns a msflib.scope.RoleLookup that reads the same attributes; the namespaces' role_lookup members are built with it. Register it once, and msflib.guard.build_guard(..., resolver=RolePermissionResolver(ROLE_PERMISSION_MAP)) and every other role check ask it for the caller's roles where each check runs, only when a role check runs:

    Attribute Role Counts when
    account role root platform:root always
    any other account role tenant:<role> is_tenant_member accepts the account at the request's tenant, or no check is given
    workspace user type workspace:<type> the request has a workspace, the account has a UserModel row in it, and is_workspace_member accepts it, or no check is given 
    from msflib.auth.roles import build_role_lookup
from msflib.scope import ROLE_LOOKUP_REGISTRY
from msflib.tenancy.deps import get_tenant_dependencies
from msflib.workspaces import is_workspace_member

tenant_deps = get_tenant_dependencies(
    session_dep=get_session, tenancy_settings=settings.scope("TENANCY")
)

ROLE_LOOKUP_REGISTRY.register(
    build_role_lookup(
        AccountModel=Account,
        UserModel=User,
        is_tenant_member=tenant_deps.is_tenant_member,
        is_workspace_member=is_workspace_member,
    )
)
ROLE_LOOKUP_REGISTRY.lock()

    Use the is_tenant_member from get_tenant_dependencies: it is bound to the tenancy settings. The bare msflib.tenancy.is_tenant_member also needs tenancy_settings and raises TypeError without it.

    The account has no tenant of its own, so pass is_tenant_member in a multi-tenant app; without it an account-level admin is an admin in every tenant.

    For roles that admins create and assign at runtime, tiers and permissions, use the guards in authz; msflib-auth does not depend on it.

    Workspace resolution¶

    get_user_dependencies(...) turns a request into a workspace and a membership. The strategy for finding the workspace is a WorkspaceResolver, chosen once at startup.

    A resolver receives a ResolverContext (session, account, path_params, headers) and returns a workspace slug, or None when the request does not identify one. Header keys in headers are lower-case. Two resolvers ship in msflib.auth.resolvers:

    Resolver Reads Default
    PathParameterResolver(param_name=...) A path parameter workspace_slug
    HttpHeaderResolver(header_name=...) A request header X-Workspace

    If you pass no resolver, PathParameterResolver() is used. HttpHeaderResolver also declares the header as an optional parameter on the dependencies, so it shows up in OpenAPI.

    Once the resolver returns a slug, the dependency looks the workspace up:

    • default resolves to the workspace with is_default = True. If none exists, the dependency returns None rather than raising.
    • current resolves to the workspace whose id is account.current_workspace_id. It is a 404 for anonymous callers and for accounts with no current workspace.
    • Any other value is matched against Workspace.slug; 404 if not found.
    • None from the resolver is a 404 with "No workspace specified."

    The namespace then exposes:

    Member Behaviour
    get_current_workspace Requires an authenticated account (get_current_account), then resolves the workspace as above.
    get_current_workspace_anonymous Same resolution without authentication.
    get_current_user Finds the UserModel row with account_id == account.id and workspace_id == workspace.id. A missing row is a 403: authenticated, but not a member of this workspace. The is_workspace_member you pass to get_user_dependencies must also accept the account (msflib.workspaces.is_workspace_member rejects banned and kicked members, allow_any_member accepts every row), otherwise the answer is 403 Not a member of this workspace. WorkspaceRoleCheck goes through it too. When UserModel is your own membership model, bind the check to it with functools.partial(is_workspace_member, user_action=UserAction[YourUser, ...]()); the unbound check reads the built-in User table and would answer 403 for your rows.
    WorkspaceRoleCheck(roles) Passes when the membership's role attribute (type by default) is in roles; otherwise 403. A workspace of another tenant than the request's is a 404.

    Behaviour may change (#269)

    get_current_workspace_anonymous does no membership or status check. It only maps a slug to a workspace row. Use it for deliberately public reads, and do not return anything from it that a non-member should not see.

    Membership is the only path to a workspace. get_current_user never grants access because the account owns the tenant or has a platform role; the account needs a membership row in that specific workspace. See workspaces for how rows are created.

    A custom resolver¶

    Subclass WorkspaceResolver for any other strategy, such as a subdomain or a claim on the account:

    from msflib.auth.resolvers import ResolverContext, WorkspaceResolver


class SubdomainResolver(WorkspaceResolver):
    def resolve(self, context: ResolverContext) -> str | None:
        host = context.headers.get("host", "")
        return host.split(".")[0] if host.count(".") >= 2 else None

    Pass an instance as workspace_resolver=. A resolver is a plain synchronous object, so it is easy to unit-test with a hand-built ResolverContext.

    One resolver applies to everything built by one get_user_dependencies call. To use two strategies in one app, call the factory twice and use each namespace on its own routers.

    Token revocation¶

    Tokens are JWTs whose sub is the account email and whose iat is the moment they were issued. Logout (and a password reset) stores the current time under the email in the keystore, and get_current_account rejects any token for that account issued up to that time. Revocation therefore applies to the account rather than to individual tokens: every session ends. Logging in again issues a later token, which is valid; the earlier ones stay revoked. The record is kept for ACCESS_TOKEN_EXPIRE_MINUTES, after which those tokens have expired anyway. If you need to end a single session, put a unique claim in the token with access_token_claims_decorator and check it in your own dependency.

    Code of your own that accepts a token outside get_current_account (a websocket or stream handshake, for example) should call msflib.core.security.verify_access_token(token, secret_key, token_store). It returns the subject after the same checks (signature, expiry, token type, revocation) and raises InvalidTokenError, or its subclass RevokedTokenError, otherwise. Decoding the JWT yourself skips the type and revocation checks.

    Token types¶

    Access, password-reset and second-factor tokens are all JWTs signed with SECRET_KEY that name the account in sub. A typ claim keeps them apart: get_current_account accepts only access, and the reset routes only password_reset. A caller's extra claims cannot set typ. A token without the claim is accepted nowhere, so tokens issued before this release stop working: everyone logs in again once after the upgrade.

    Password reset¶

    One reset is pending per account, kept in the key store: a new request replaces the code and the link of the previous one. The six-digit code is the weak part, so it expires sooner than the link, allows PASSWORD_RESET_MAX_ATTEMPTS wrong guesses in total (across /verify-token and /reset-password). After the last one neither the code nor the link works, and a new reset can be requested once PASSWORD_RESET_MIN_INTERVAL_SECONDS have passed since the last one was sent. Code and link both stop working once the password is set. The limits are per account; limiting requests per client address belongs in the host or the proxy.

    Because the pending reset lives in the key store, use RedisStore in production: with the in-memory MapStore, a restart discards pending resets and several workers do not share them.

    A key store of your own must implement put_if, remove and remove_if as single steps (see StoreInterface). The email lock relies on remove_if: a holder releases the lock only while it still owns it, so a holder whose lock expired never frees someone else's. The codes rely on put_if: every change to a pending code (a counted wrong guess, the mark that it was used, a new code) is written only over the record that was read. So when requests arrive together a code is accepted once, each wrong guess is counted, one code is sent, and a code that was replaced or used is never written back. A login that waits for its second factor relies on remove, which hands the record to one request.

    One-time codes¶

    Password reset, email verification and login by code all send a six-digit code by email, and share one set of rules (msflib.auth.services.codes.OneTimeCodeManager): one pending code per account and purpose, a short lifetime, a limited number of wrong guesses, single use, and a pause before another is sent. Neither using a code nor using up its guesses shortens the pause: the code stops working, and the next one is sent only after the pause has passed since it was sent. A code works only for the purpose it was sent for. The endpoints that send one answer the same way whether or not the email is registered, also when sending fails: the error is logged, and the code (or the reset) is dropped so the user can ask again at once. The email is sent after the lock described under "When the email changes" is released, so a slow mail server never holds up an email change.

    Sending is split in two. Core's msflib.services.email renders a template and sends it, and knows nothing about auth. msflib.auth.services.email adds what only auth knows: it reads the AUTH settings, and calls your override when you pass one. Verification and login codes go through core's send_otp_email and the verify_email.html template, which receives valid_for (for example "10 minutes"); the subject says "Email Verification" or "Login Code". The reset email's template receives valid_hours for the link and code_minutes for the code. Pass send_code_email_override(email_to, username, code, action) to the router to send them your own way.

    Email verification¶

    Auth sends and checks the code; where the result is kept is passed in, so auth does not depend on the account module. msflib-account keeps it in its identity_verification table:

    from msflib.account.services.verification import IdentityVerifier
from msflib.auth.eventbus import register_event_hooks

verification = IdentityVerifier()          # email; the table also holds phone
auth_router = router(..., email_verification=verification)

# Optional: react to accounts being registered and to their email changing.
register_event_hooks(
    emitter=app_emitter,
    settings=settings,
    token_store=token_store,                # the store the router's get_keystore returns
)
    • At registration. With SEND_VERIFICATION_ON_REGISTRATION=true the hook sends the code when the account module emits account-created. The setting is read on each event, so it can be switched without rewiring.
    • When the email changes. Tokens, resets and codes are all issued for an email. When the account module emits account-updated-strict with email in its changes, the hook revokes the access tokens of the old email and drops its pending reset and codes, so none of them can be used on an account that takes that email later. Without register_event_hooks they stay valid until they expire. A login that is waiting for its second factor is tied to the account's id as well as its email, so it cannot be finished once the email has changed, with or without the hook. The event is strict and comes before the update is committed: if the key store fails, the error is raised and the email change is rolled back, so an email never changes while what was issued for the old one still works. The old email is also locked in the key store from the cleanup until the update is committed (account-updated), and every route that issues something for an email (login, the second-factor step, Google login, login and verification codes, password recovery) takes the same lock before it looks up the account. A login writes last_login_date and emits account-logged-in after the lock is released, so it never waits on an email change that holds the account row. Email verification and the password change of a reset take it too, so a code or reset checked for the old email cannot then be applied to an account that has changed or taken that email. So nothing can be issued for the old email between the cleanup and the commit. A route that waits longer than EMAIL_LOCK_WAIT_SECONDS for the lock answers 503; the second-factor step then keeps the pending login, with its wrong guesses, for a retry. An email change that waits that long fails with EmailLockedError, a ServiceUnavailableError, which core's exception handlers answer with 503. If the update is rolled back after the cleanup, the lock lasts until it expires (EMAIL_LOCK_HOLD_SECONDS).
    • POST /email-verification with {"email"} sends a code to an account whose email is not verified. It is the resend: for a code that expired, ran out of guesses or never arrived, for accounts that existed before verification was turned on, for an account whose email changed, and for accounts created by another route than registration.
    • POST /verify-email with {"email", "code"} records the email as verified and emits account-email-verified.
    • REQUIRE_EMAIL_VERIFICATION=true refuses every login with 403 "Email not verified" until then. The router refuses to start with it when no email_verification is given.
    • A Google login whose verified_email is true, and a login by code, both prove the address and record it.

    Without email_verification the two routes answer as usual and do nothing. Any object with is_verified(*, session, account) and mark_verified(*, session, account) can stand in for IdentityVerifier. The shape (msflib.auth.services.verification.IdentityVerifier) is not tied to email: one verifier covers one kind of identity, and the router takes the one for email as email_verification. The codes themselves (OneTimeCodeManager) are keyed by recipient, so a phone number works the same way once there is a sender for it.

    Login by code¶

    With ENABLE_OTP_LOGIN=true, POST /login/otp/request with {"email"} sends a code to an active account, and POST /login/otp with {"email", "code"} returns the usual login response. The code takes the place of the password, so whoever can read the account's mailbox can log in; that is already true of password reset. A second factor, when one is configured, is asked whether it is still required after the code: one of another kind (an authenticator app, SMS) should be, one that is itself an email code adds nothing.

    Second factor¶

    Pass second_factor= to the router to add a step after the password. It is an object with three methods, each called with keyword arguments:

    class Totp:
    def required(self, *, session, account, first_factor) -> bool:
        return account.totp_secret is not None

    def challenge(self, *, session, account) -> dict | None:
        return {"method": "totp"}          # sent to the client; send an SMS here if that is the method

    def verify(self, *, session, account, code: str) -> bool:
        return pyotp.TOTP(account.totp_secret).verify(code)

    required is told how the first step was passed, as a msflib.auth.models.FirstFactor: password, email_code (login by code) or google. A second factor only helps when it proves something the first step did not, so a factor that sends its code by email should return false after FirstFactor.email_code; otherwise the user reads two codes from the same mailbox and nothing is gained. An authenticator app or SMS factor ignores the argument.

    When required is true, POST /login (and the Google callback and login by code) answers 202 with {"second_factor_required": true, "challenge_token": "...", "challenge": {...}} and no access token. The client then posts {"challenge_token", "code"} to POST /login/second-factor and receives the usual login response.

    The router keeps the order safe: a challenge token is issued only after the first step succeeded, is recorded in the key store, works once, expires after SECOND_FACTOR_CHALLENGE_EXPIRE_MINUTES and allows SECOND_FACTOR_MAX_ATTEMPTS wrong codes. A code without a challenge, or a challenge the router did not issue, is refused, so the second factor can never stand in for the password. A challenge token is not an access token. Enrolment (creating and storing the secret) is the host's.

    Events¶

    Event names are in msflib.auth.eventbus.EventName:

    Event Emitted when
    account-logged-in A login or Google callback succeeds. Optional: no listener is fine.
    google-account-create A Google login names an unknown email and ALLOW_GOOGLE_OAUTH_SIGNUP is true. Required: a listener must create the account, or the callback returns 500.
    account-email-verified An account's email is recorded as verified: by /verify-email, a login by code, or a Google login with a verified address. Optional.

    Register the listener on the app emitter, for example @app_emitter.on("google-account-create") with app_emitter = bind_app_emitter(app). A listener added with emitter.on(...) at import time lands on the default emitter, which the router does not see, and the callback returns 500 "No listener". Sync and async listeners on the app emitter both work.

    See Event bus for registering listeners.

    Examples¶

    Protect routes by account role and workspace membership¶

    This runs against an in-memory SQLite database using the models from msflib-account and msflib-workspaces. member and guest are workspace roles; the owner passes WorkspaceRoleCheck.

    from datetime import timedelta

from fastapi import Depends, FastAPI
from fastapi.testclient import TestClient
from msflib.account.models.account import Account
from msflib.auth.deps import get_account_dependencies, get_user_dependencies
from msflib.auth.resolvers import PathParameterResolver
from msflib.core.security import create_access_token
from msflib.core.store import MapStore
from msflib.scope import (
    ROLE_LOOKUP_REGISTRY,
    get_member_account_dependency,
    no_workspace,
)
from msflib.tenancy.deps import get_tenant_dependencies
from msflib.workspaces import is_workspace_member
from msflib.workspaces.models import UserType
from msflib.workspaces.models.user import User
from msflib.workspaces.models.workspace import Workspace

# get_session, get_keystore, settings and SECRET_KEY come from your app; see "Wiring".
tenant_deps = get_tenant_dependencies(
    session_dep=get_session, tenancy_settings=settings.scope("TENANCY")
)
account_deps = get_account_dependencies(
    AccountModel=Account,
    oauth_token_url="/login",
    secret_key=SECRET_KEY,
    session_dep=get_session,
    keystore_dep=get_keystore,
    get_current_tenant=tenant_deps.get_current_tenant,
    get_current_workspace=no_workspace,
)
user_deps = get_user_dependencies(
    UserModel=User,
    WorkspaceModel=Workspace,
    session_dep=get_session,
    account_dependencies=account_deps,
    is_workspace_member=is_workspace_member,
    workspace_resolver=PathParameterResolver(),
)
ROLE_LOOKUP_REGISTRY.register(user_deps.role_lookup)
ROLE_LOOKUP_REGISTRY.lock()

app = FastAPI()


get_member_account = get_member_account_dependency(
    get_session=get_session,
    get_current_account=account_deps.get_current_account,
    get_current_tenant=tenant_deps.get_current_tenant,
    get_current_workspace=user_deps.get_current_workspace,
    is_workspace_member=is_workspace_member,
)


@app.get("/{workspace_slug}/whoami", dependencies=[Depends(get_member_account)])
def whoami(
    workspace=Depends(user_deps.get_current_workspace),
    user=Depends(user_deps.get_current_user),
):
    return {"workspace": workspace.slug, "user_id": user.id, "type": user.type}


@app.get(
    "/{workspace_slug}/admin",
    dependencies=[
        Depends(user_deps.WorkspaceRoleCheck([UserType.owner, UserType.admin]))
    ],
)
def admin_only():
    return {"ok": True}


@app.get("/{workspace_slug}/public")
def public(workspace=Depends(user_deps.get_current_workspace_anonymous)):
    return {"workspace": workspace.slug}


token = create_access_token("ada@example.com", SECRET_KEY, timedelta(minutes=5))
client = TestClient(app)
client.get("/acme/whoami", headers={"Authorization": f"Bearer {token}"})
# 200 {"workspace": "acme", "user_id": 1, "type": "owner"}   (ada is a member)
# 403 {"detail": "Not a member of this workspace."}  (non-member or inactive)
# GET /nope/public -> 404 "Workspace not found"

    Resolve the workspace from a header¶

    from msflib.auth.resolvers import HttpHeaderResolver
from msflib.workspaces import is_workspace_member

user_deps = get_user_dependencies(
    UserModel=User,
    WorkspaceModel=Workspace,
    session_dep=get_session,
    account_dependencies=account_deps,
    is_workspace_member=is_workspace_member,
    workspace_resolver=HttpHeaderResolver("X-Workspace"),
)

    Routes no longer carry a {workspace_slug} path segment. A client sends X-Workspace: acme; without the header the dependency responds 404 "No workspace specified.". X-Workspace: current selects the account's current_workspace_id, and X-Workspace: default the default workspace.

    Add claims and extra response fields at login¶

    The response model filters what the login route returns, so extra fields need a response type that declares them.

    from msflib.auth.models import Token


class LoginResponse(Token):
    environment: str = ""


app.include_router(
    auth_router(
        get_session=get_session,
        get_keystore=get_keystore,
        get_current_account=account_deps.get_current_account,
        account_type=Account,
        account_read_type=AccountRead,
        settings=settings,
        access_token_response_type=LoginResponse,
        access_token_claims_decorator=lambda account, ctx: {
            "email_domain": account.email.split("@")[1]
        },
        access_token_decorator=lambda payload, ctx: {
            **payload,
            "environment": "staging",
        },
    )
)

    ctx is {"session": session}. The JWT now carries an email_domain claim and the login body includes environment. The workspaces module ships WorkspaceAction.build_access_token_claims and decorate_access_token_payload, which are designed for these two hooks and add the active workspace and membership.

    Troubleshooting¶

    Symptom Cause and fix
    401 "Could not validate credentials" The token is malformed, expired, or signed with a different key. secret_key passed to get_account_dependencies must equal settings.SECRET_KEY used by the router.
    401 "Token expired" right after logout Expected: logout revoked every token issued up to then. Log in again for a new one; the old ones stay revoked.
    403 "Email not verified" at login REQUIRE_EMAIL_VERIFICATION is on and the account's current email has not been verified. Send a code with POST /email-verification and confirm it with POST /verify-email.
    400 "Invalid token" for a reset code that was right The code expired (PASSWORD_RESET_CODE_EXPIRE_MINUTES), was used, was replaced by a newer request, or ran out of guesses. Request the reset again.
    404 "No workspace specified." The resolver returned None: the path parameter name does not match the route, or the header is missing.
    404 "Current workspace unknown for anonymous user." The slug current was used on an anonymous dependency.
    403 "User not found in specified workspace" The account has no membership row in that workspace. Create one (see workspaces).
    403 on an admin route for a root account RoleCheck and WorkspaceRoleCheck match exactly. Add root to the list, or use get_current_active_superuser.
    Google callback returns 500 "No listener for Google account creation" ALLOW_GOOGLE_OAUTH_SIGNUP is on but nothing listens to google-account-create. Register a listener that creates the account.
    Reset email contains the wrong link host The link is CORE.CLIENT_HOST plus AUTH.PASSWORD_RESET_PATH. Set both.
