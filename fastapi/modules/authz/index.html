    msflib-authz¶

    Purpose¶

    msflib-authz stores roles and their permissions in the database and assigns them to accounts at runtime. It answers two questions:

    • Does this account hold permission X here? (RoleService.has_permission, the require_permission guard)
    • Which roles does this account hold here? (RoleService.get_role_keys_for, the require_role guard)

    It sits beside the simple role attributes (Account.role, User.type) that auth guards compare, rather than replacing them. Apps pick either way, or both; see Two ways to guard a route and Legacy roles. msflib-auth does not depend on this module.

    The terms tier, owner and assignment scope are easy to confuse because they all mention tenants and workspaces. Read Three questions about a role before the rest.

    Install¶

    [tool.poetry.dependencies]
msflib = { git = "https://github.com/msflib/fastapi.git", subdirectory = "core", rev = "core-v0.2.2" }
msflib-tenancy = { git = "https://github.com/msflib/fastapi.git", subdirectory = "modules/tenancy", rev = "tenancy-v0.2.1" }
msflib-authz = { git = "https://github.com/msflib/fastapi.git", subdirectory = "modules/authz", rev = "authz-v<version>" }

    Use the release tag of the version you want; do not pin dev. The package depends on core and tenancy. Its names load lazily, so importing msflib.authz does not register the table models; import msflib.authz.models before you create tables.

    Wiring into a host app¶

    1. Add the role, role_permission, role_assignment, group, group_member and resource_access tables to your schema. An app that already created the first three must add group and group_member before it upgrades: role and permission checks read group_member to expand a user's groups, so they fail with a missing-table error until it exists. The package ships no migrations: import msflib.authz.models before SQLModel.metadata.create_all, or include the tables in your own migrations (see How a module is wired). An app that created group from the groups release also has group.workspace_id as NOT NULL, and create_all never alters an existing column. Make it nullable before you create a group with workspace_id=None (the workspace-agnostic bucket); on PostgreSQL that is ALTER TABLE "group" ALTER COLUMN workspace_id DROP NOT NULL.
    2. Register permission keys at import time.
    3. Seed the system roles at startup, after every module has registered its keys.
    4. Build the guards with get_authz_dependencies and protect routes with require_permission or require_role.

    Register permission keys¶

    from msflib.authz import PERMISSION_REGISTRY

PERMISSION_REGISTRY.register("documents.share", tenant_cascade=True)

    tenant_cascade decides whether a tenant-tier role grants the permission inside a workspace. A permission that should only ever be held through workspace membership leaves it off.

    tiers limits which roles may hold a key (default: any). authz.manage_roles is registered for the platform and tenant tiers only. A role of another tier is ignored for that key during resolution, however the key reached it (including a prefix.* wildcard), and add_permissions rejects an exact key the role's tier may not hold. The seeded workspace roles leave such keys out.

    PERMISSION_REGISTRY.register("ops.reset", tiers=(RoleTier.platform,))

    Registering the same key twice is fine unless tenant_cascade or tiers differ, which raises ValueError.

    Seeding¶

    from msflib.authz.seed import (
    backfill_account_role_assignments,
    seed_role_permissions,
    seed_system_roles,
)

roles = seed_system_roles(session, default_tenant_id=tenant_id)
seed_role_permissions(session, roles=roles)  # after every module has registered its keys
backfill_account_role_assignments(
    session, roles=roles, default_tenant_id=tenant_id, accounts=[(a.id, a.role) for a in accounts]
)
    Seeded role Tier Owner Permissions
    root platform none every registered key a platform role may hold
    admin tenant default tenant every registered key a tenant role may hold
    user tenant default tenant none
    owner, admin workspace none (template) every key a workspace role may hold (so not authz.manage_roles, nor a prefix.* key covering it)
    member, guest workspace none (template) none

    All the seeders are idempotent, safe to run from several processes at once, and run on every startup. Each is one unit of work and commits once at the end. seed_system_roles refuses, with RoleExistsError, to adopt a custom role that already holds a seeded identity (same key, tier and owner), and commits nothing in that case.

    The backfills mirror the legacy attributes into assignments with source="legacy_backfill". The source is part of an assignment's identity: a runtime grant and the mirror of the same role are two rows, so a runtime grant (even an expired one) never blocks, renews or revokes the mirror, and the backfill never touches a runtime row. Callers cannot set the source: grant and ensure_assignment always write runtime rows.

    • backfill_account_role_assignments mirrors (account_id, Account.role): root as a platform assignment, admin and user as tenant assignments in the default tenant.
    • backfill_workspace_membership_role_assignments mirrors (account_id, workspace_id, tenant_id, User.type) as workspace assignments. It is not wired into the test site because that app has no workspace model; pass it your memberships.

    Pass the complete set

    A backfill treats its input as the whole truth. It revokes every legacy_backfill assignment the input no longer implies, including those of accounts or memberships that are missing from it, which is how deleted accounts and removed memberships lose their mirrored role. A partial list therefore revokes too much. An empty list does nothing, so a snapshot that failed to load cannot revoke every mirror; the stale mirrors of a table that really became empty must be revoked by hand. Runtime grants (source="runtime") are never touched.

    Both backfills are transitional and go away once assignments replace the legacy attributes.

    Guards¶

    require_permission¶

    get_authz_dependencies(session_dep=..., get_current_account=..., get_current_tenant=..., get_current_workspace=..., is_workspace_member=...) returns a namespace with require_permission(key, tier=...):

    from msflib.tenancy.deps import get_tenant_dependencies

tenant_deps = get_tenant_dependencies(session_dep=get_session, settings=settings)
authz = get_authz_dependencies(
    session_dep=get_session,
    get_current_tenant=tenant_deps.get_current_tenant,
    get_current_account=account_deps.get_current_account,
    get_current_workspace=user_deps.get_current_workspace,
    is_workspace_member=is_workspace_member,
)

router.get(
    "/{workspace_slug}/docs",
    dependencies=[Depends(authz.require_permission("documents.share"))],  # workspace tier
)
router.get(
    "/tenant-settings",
    dependencies=[Depends(authz.require_permission("documents.share", tier="tenant"))],
)
router.get(
    "/ops",
    dependencies=[Depends(authz.require_permission("authz.manage_roles", tier="platform"))],
)
    • The default tier is workspace. Workspace guards resolve the workspace from the request; tenant and platform guards never do.
    • An unknown tier raises ValueError when the dependency is built.
    • tier="platform" is satisfied only by platform-tier roles.
    • get_current_tenant and get_current_account are required. A request with no tenant is denied. An app that does not deal with tenancy passes the get_current_tenant from get_tenant_dependencies, which supplies the default tenant.
    • A workspace that belongs to a different tenant than the request is denied.
    • get_current_workspace is optional but comes with is_workspace_member (msflib.workspaces.is_workspace_member, or allow_any_member for a host without membership rules). Workspace guards deny an account the check rejects. Building a workspace guard without the pair raises ValueError, so a misconfigured app fails at startup instead of denying every request. Tenant and platform guards need only tenant and account.

    A guard passes when the caller holds a role, at a tier that reaches the request, that bundles the key (or a prefix.* key covering it):

    Guard tier Satisfied by
    workspace (default) a workspace-tier role held in this workspace; a tenant-tier role of the request's tenant, only if the key is registered tenant_cascade=True; a platform-tier role
    tenant a tenant-tier role of the request's tenant; a platform-tier role
    platform a platform-tier role only

    Denied, with 403, when:

    • the key is not registered in this process (a warning is logged, so a typo never grants). A bundled key that is no longer registered counts for nothing either, so every process that checks permissions, including workers and CLIs, must import the modules that register the keys;
    • no account can be identified, or a wired get_current_tenant returns no tenant;
    • the workspace belongs to another tenant, or a workspace guard has no workspace in the request;
    • the matching assignment is expired, or its scope does not fit its role's tier.

    Prefer require_permission for new code: a permission names what may be done, and does not depend on what the roles happen to be called. Use require_role when the route is about holding a role.

    To check a permission outside a route, for example inside a service, call RoleService.has_permission with the account, tenant and (for workspace permissions) workspace (see How a permission is resolved).

    require_role¶

    Depends(authz.require_role(RoleKey(tier, key), ...)) passes when the caller holds any of the roles. Each key is matched at its own tier: a platform role anywhere, a tenant role in the request's tenant, a workspace role in the request's workspace.

    from msflib.authz import RoleKey, RoleTier

router.get(
    "/ops",
    dependencies=[Depends(authz.require_role(RoleKey(RoleTier.platform, "root")))],
)
router.get(
    "/{workspace_slug}/admin",
    dependencies=[
        Depends(
            authz.require_role(
                RoleKey(RoleTier.workspace, "admin"), RoleKey(RoleTier.tenant, "admin")
            )
        )
    ],
)
    • It takes RoleKey only. A bare string raises TypeError when the dependency is built, and no keys raises ValueError.
    • The same key at another tier does not satisfy it: a tenant admin is not a workspace admin.
    • A guard with a workspace-tier key needs a workspace in the request and denies without one. Tenant and platform keys never resolve a workspace.
    • Tenant and workspace handling is the same as for require_permission: the request's tenant (denied when missing), a workspace of another tenant denied, account identified from the membership pair or get_current_account.
    • A tenant-tier key is held at a workspace route too: a tenant admin passes require_role(RoleKey(RoleTier.tenant, "admin")) on a workspace route. Unlike require_permission, there is no tenant_cascade switch, because the caller named the tenant role explicitly.
    • It reads assignments only. The legacy attributes do not count (see Legacy roles).

    Prefer require_permission where the guard names an action, and require_role where it names a role.

    Two ways to guard a route¶

    msflib-auth msflib-authz
    Guards RoleCheck, WorkspaceRoleCheck require_permission, require_role
    Reads Account.role, User.type attributes role assignments in the database
    Needs nothing beyond your account and user models the six authz tables, seeding
    Granularity a role name, exact match tier, owner and scope; permissions bundled into roles
    Changed at runtime by editing the attribute by granting or revoking assignments

    Both are supported. Use auth when a role attribute is enough. Use authz when you need roles that admins create and assign at runtime, per-workspace or per-tenant roles, or permissions. The module routers that take a role guard parameter (role_check, workspace_role_check, admin_role_check or mutation_role_check: account admin, notifications, workspaces, workspace config, workspace notifications, ai_core and ingestion) use the auth way, because they pass plain legacy role values.

    Configuration¶

    msflib-authz has no settings of its own. It resolves the tenant through the get_current_tenant you pass; see tenancy for the default-tenant one.

    Key concepts¶

    Three questions about a role¶

    Every row in role_assignment says "this principal holds this role, here". Three separate things decide what that means, and each lives in a different place.

    Question Answered by Stored on
    What level of authority does the role grant? the role's tier: platform, tenant or workspace Role.tier
    Who defined the role, and who may use it? the role's owner: nobody (shared), a tenant, or a workspace Role.tenant_id, Role.workspace_id
    Where does this one grant apply? the assignment's scope RoleAssignment.tenant_id, RoleAssignment.workspace_id

    Role.tenant_id is the owner, not the scope

    The tenant_id and workspace_id columns on Role say where the role is defined. They never say where the role applies. A role's authority is decided by its tier together with each assignment's own tenant_id and workspace_id. The columns on the two tables share names, but they are different facts.

    The columns are deliberately not named owner_tenant_id / owner_workspace_id: the longer name adds noise without removing the need to read this section. Whenever you see role_tenant_id / role_workspace_id in the code (for example in validation.py), it is the owner; assignment_tenant_id / assignment_workspace_id is the scope of a grant.

    Tier¶

    The tier fixes what shape of scope an assignment must have, and how far the role reaches.

    Tier Assignment tenant_id Assignment workspace_id Reaches
    platform NULL NULL everywhere
    tenant set NULL that tenant (and, for cascading permissions, its workspaces)
    workspace set set exactly that workspace

    Consequences:

    • A tenant or platform role cannot be assigned "at a workspace". Giving a tenant-tier role a workspace_id is invalid, and so is giving a workspace-tier role no workspace_id. Only workspace-tier roles are assigned to a workspace. A tenant-tier role reaches workspaces through the tenant cascade, not through a workspace assignment.
    • A platform role must be assigned with both ids NULL. NULL ids are not what makes a role platform-wide: the role's tier does. NULL ids on an assignment of a tenant or workspace role are simply invalid, and such a row grants nothing.
    • A workspace_id always requires a tenant_id; a workspace belongs to a tenant.

    Owner¶

    The owner restricts who may be granted the role. NULL means "no restriction".

    Role owner (tenant_id, workspace_id) Meaning May be assigned
    (NULL, NULL) shared definition in any tenant or workspace its tier allows
    (T, NULL) defined by tenant T only inside tenant T
    (T, W) defined by workspace W of tenant T only inside workspace W

    The seeded owner, admin, member and guest workspace roles are shared (NULL, NULL): one definition, assigned per workspace, with every assignment naming its own tenant and workspace. The seeded tenant roles (admin, user) are owned by the default tenant.

    A tier and an owner are independent. A workspace-tier role can be shared, owned by a tenant (a per-tenant template) or owned by one workspace. A platform-tier role must have no owner. A tenant-tier role cannot be owned by a workspace.

    Assignment scope¶

    RoleAssignment.tenant_id / workspace_id say where this grant applies, for example "Ada is an admin in tenant 5", or "Grace is a member of workspace 12 in tenant 5". Which ids are required follows from the tier (above), and the ids must lie inside the role's owner (above).

    Valid and invalid combinations¶

    An assignment is effective, meaning it can grant authority, only if all three of the following hold. This single rule is is_effective_assignment in validation.py; every resolution path uses it.

    1. Its scope has the shape its role's tier requires (the table under Tier).
    2. It lies inside the role's owner. For each of tenant and workspace: if the role has an owner there, the assignment must name exactly that id; if the role has none, any id is fine.
    3. It has not expired (expires_at is NULL or in the future).

    The owner check only compares when the role has an owner, because a NULL owner means "shared". That asymmetry is intentional, and it does not leave the assignment's own NULLs unchecked:

    • If the role has an owner, a NULL assignment id fails the comparison (NULL is not equal to 5).
    • If the role is shared, a NULL assignment id is caught by the tier-shape check in step 1.

    The two checks together cover every case:

    Role (tier; owner) Assignment (tenant, workspace) Effective? Why
    platform; (NULL, NULL) (NULL, NULL) yes
    platform; (NULL, NULL) (5, NULL) no shape: platform needs no ids
    tenant; (NULL, NULL) shared (5, NULL) yes shared, tenant named
    tenant; (NULL, NULL) shared (NULL, NULL) no shape: tenant tier needs a tenant
    tenant; (5, NULL) (5, NULL) yes
    tenant; (5, NULL) (6, NULL) no owner: role is tenant 5's
    tenant; (5, NULL) (5, 3) no shape: tenant tier has no workspace
    workspace; (NULL, NULL) template (5, 3) yes
    workspace; (NULL, NULL) template (5, NULL) no shape: workspace tier needs a workspace
    workspace; (5, NULL) (5, 3) yes any workspace of tenant 5
    workspace; (5, NULL) (6, 3) no owner: role is tenant 5's
    workspace; (5, 3) (5, 3) yes
    workspace; (5, 3) (5, 4) no owner: role is workspace 3's
    workspace; (5, 3) (NULL, NULL) no shape and owner

    RoleService.grant rejects an invalid assignment with ValueError. Resolution also ignores one, so a row that was written some other way (a raw action, a data migration, a bug) still grants nothing. The database enforces what it can without joining tables:

    • ck_role_tier_scope on role: platform roles have no owner; tenant roles have no workspace owner; a workspace owner implies a tenant owner.
    • ck_role_assignment_scope on role_assignment: a workspace_id requires a tenant_id.
    • ck_role_assignment_source on role_assignment: source is runtime or legacy_backfill.
    • ck_role_scope_ids_positive and ck_role_assignment_ids_positive: scope ids, when set, are positive. The unique identity indexes treat NULL scope columns as equal by coalescing them to -1, so a real id must never equal the sentinel; RoleService also rejects non-positive ids with ValueError.

    The tier-versus-assignment rule (step 1) and the owner rule (step 2) compare columns on two tables, which a CHECK constraint cannot do. They are enforced by the service on write and by resolution on read.

    How a permission is resolved¶

    RoleService.has_permission(session, account_id=..., tenant_id=..., workspace_id=None, permission_key=...) loads the account's effective assignments for that scope, including those made to a group the account belongs to, and then applies the reach of each tier:

    • platform: always applies.
    • tenant: applies when the assignment's tenant is the request's tenant, and either the request is tenant-level (no workspace) or the permission was registered with tenant_cascade=True.
    • workspace: applies only when the assignment's (tenant_id, workspace_id) is exactly the request's pair. There is no cascade.

    The permission is granted when any matching role bundles the key (or a prefix.* key covering it). platform_only=True considers platform-tier roles only.

    Role keys¶

    get_role_keys_for(session, principal_kind=..., principal_id=..., tenant_id=None, workspace_id=None) returns the keys of the roles in effect at a scope, as RoleKey(tier, key) values. The tier is part of the value because the same string can exist at several tiers: the seeded admin is a tenant role and a workspace role. Without the tier, a workspace admin could be mistaken for a tenant admin.

    • Platform roles are always included.
    • Tenant roles are included for tenant_id.
    • Workspace roles are included for exactly (tenant_id, workspace_id).
    • With tenant_id=None, only platform roles are returned.

    Legacy roles¶

    Account.role (root, admin, user) and User.type (owner, admin, member, guest) are read by the auth guards. The authz guards ignore them: only assignments and their bundled permissions count.

    To move a route from RoleCheck to require_role without losing access, mirror the attributes into assignments first with the backfills (see Seeding). They write legacy_backfill assignments; a runtime grant is a separate row. The two sources are independent afterwards: revoking an assignment does not change the attribute, and editing the attribute does not change assignments until the backfill runs again.

    The seeded role keys reuse the legacy values so the backfills mirror existing data. The shared names are safe because they live at different tiers and every authz check is tier-aware: a legacy admin becomes a tenant-tier admin, root a platform-tier root.

    Writing roles¶

    Write through RoleService; the actions are plain data access.

    • create_role, ensure_role (get-or-create), add_permissions, grant, ensure_assignment (get-or-grant), revoke. The values the server decides are separate parameters, not schema fields: owner=RoleOwner(...) (default SHARED), is_system and created_by_account_id for a role; scope=RoleAssignmentScope(...) (default UNSCOPED) and granted_by_account_id for an assignment. Renewing an expired grant keeps its original grantor unless a new one is passed. The ensure_* methods are safe to repeat and to run from several processes at once: a caller that loses a creation race gets the winner's row.
    • Each public method is one closed unit of work: its writes run in savepoints and it commits once at the end, so a failure leaves nothing half-written. The batch methods (ensure_roles, bundle_permissions, sync_legacy_assignments, used by the seeders) commit once for the whole batch. Events fire on that commit. Because the commit is the session's, any other pending work in the same session is committed with it.
    • grant validates the assignment (tier shape, owner scope, expires_at in the future) and rejects an existing one with AssignmentExistsError; create_role raises RoleExistsError for a duplicate. Both are ValueError subclasses, and they are raised the same way when a concurrent writer wins the race, so callers handle one error rather than a raw IntegrityError.
    • Granting over an expired runtime assignment renews it (new expires_at; the original granter is kept unless granted_by_account_id is given) instead of failing, so an expired grant never blocks re-granting. A mirrored legacy assignment of the same role is a separate row and is left alone.
    • key, name and principal_id are trimmed, must not be blank, and keys and principal ids are limited to 255 characters; scope ids must be positive.
    • Events: see Events.

    A row written straight through an action is not validated, but resolution ignores it if it breaks the rules above.

    Groups¶

    A group is a set of accounts that can hold role assignments together. Assign a role to a group with principal_kind=PrincipalKind.group and the group's id as principal_id; every account that is a member then holds it, in addition to its own assignments. This applies when the principal is a user (an account); a group is not a member of another group. Resolution nests the account's memberships as a subquery, so the query size does not grow with the number of groups.

    Visibility Who manages membership Who gets the group's roles
    workspace not restricted by the service; your route guard decides every member
    personal only the group's owner every member

    A group belongs to a workspace, or to the workspace-agnostic bucket when its workspace_id is None (a real scope of its own, not "unscoped"). GroupService adds and removes members. Each call is one unit of work, like RoleService:

    from msflib.authz.models import GroupMemberCreate
from msflib.authz.services import GroupService

service = GroupService()
service.add_member(
    session,
    data=GroupMemberCreate(account_id=42),
    group_id=group.id,
    added_by_account_id=current_account.id,
)
service.remove_member(session, id=member.id, removed_by_account_id=current_account.id)

    group_id and the acting account come from the request, so they are service parameters, not fields of GroupMemberCreate. For a personal group the acting account must be the owner, otherwise ValueError. Adding an account that is already a member raises GroupMemberExistsError, also when two requests race. GroupCreate likewise has no workspace_id or owner_account_id; pass them with create(update={...}).

    Resource access¶

    A resource access row gives one user or group a level on one resource, for example a file. Roles answer "what may this account do here"; access rows answer "what may this account do to this one thing". They are independent: AccessService never reads roles. The word permission in this module always means a permission key such as docs.publish; a level on a resource is an access level.

    Level Meaning
    none explicit exclusion; blocks access inherited from a parent
    viewer read
    commenter read and comment
    editor read, comment and edit
    manager everything, including sharing

    Resolution walks the resource and then its ancestors, nearest first. At the first level that has an access row for the account (directly, or through a group it belongs to) the highest matching level wins, none included, and farther ancestors are not consulted. No match gives None. The resource's owner is always manager. Use the can_read, can_comment, can_edit and can_manage helpers to turn a level into a yes or no.

    from msflib.authz.models import AccessLevel, PrincipalKind, ResourceAccessCreate
from msflib.authz.services.access import AccessService, can_edit

service = AccessService()
service.grant(
    session,
    data=ResourceAccessCreate(
        principal_kind=PrincipalKind.user,
        principal_id="42",
        level=AccessLevel.editor,
    ),
    resource_type="drivelink_node",
    resource_id=12,
    workspace_id=7,
    granted_by_account_id=current_account.id,
)
level = service.resolve_access(
    session,
    resource_type="drivelink_node",
    resource_id=12,
    workspace_id=7,
    account_id=42,
    is_owner=False,
    ancestor_ids=[3, 1],
)
assert can_edit(level)

    principal_id must be the user's account id or the group id as a positive integer without leading zeros ("42", not "042"); anything else raises a validation error, because resolution compares it as a string and such a row could never match. The resource (resource_type, resource_id), its workspace_id (None is the workspace-agnostic bucket, a real scope of its own) and the acting account come from the request, so they are parameters of grant, not fields of ResourceAccessCreate, which holds only the principal and the level. resource_type is 1 to 64 characters and resource_id positive, otherwise ValueError. Granting again to the same principal updates the level, records the new grantor when one is passed (otherwise the original stays), and keeps the original workspace_id. revoke deletes an access row. resolve_access and resolve_accesses take the resource's workspace_id and count only rows granted in exactly that workspace (None matches only the workspace-agnostic bucket, not every workspace), so a grant in workspace 7 never authorizes the same resource id in workspace 8. For lists, resolve_accesses resolves many resources at once: one query for the account's groups and one access query per 500 distinct resource ids (a single batch for most lists).

    Events¶

    RoleService emits two events, role-assignment-granted and role-assignment-revoked, with RoleAssignmentEventName.ROLE_ASSIGNMENT_GRANTED and RoleAssignmentEventName.ROLE_ASSIGNMENT_REVOKED. GroupService emits group-member-added and group-member-removed, named GroupMemberEventName.GROUP_MEMBER_ADDED and GroupMemberEventName.GROUP_MEMBER_REMOVED. AccessService emits resource-access-granted and resource-access-revoked, named ResourceAccessEventName.RESOURCE_ACCESS_GRANTED and ResourceAccessEventName.RESOURCE_ACCESS_REVOKED. Import the names and the payload contracts from the package's eventbus.

    from msflib.authz.eventbus import EVENT_CONTRACTS, RoleAssignmentEventName
from msflib.eventbus import get_emitter

def on_granted(row, payload): ...

get_emitter().on(RoleAssignmentEventName.ROLE_ASSIGNMENT_GRANTED, on_granted)
    • When. After the outermost commit of the unit of work, never before. A rollback discards them. A listener error is logged, not raised, so it cannot undo the write.
    • Arguments. row is a snapshot of the written row's columns, taken before the commit: for a role assignment id, role_id, principal_kind, principal_id, tenant_id, workspace_id, source and so on; for a group member group_id and account_id; for resource access resource_type, resource_id, principal_kind, principal_id, level, workspace_id and so on. It stays readable after the session is closed, so a listener may run later or on another thread. It is not the ORM instance. For revoked it is the row as it was before it was deleted.
    • payload. For role assignments: principal_kind, principal_id, role_key, tenant_id, workspace_id; role_key is left out when the role row no longer exists. For group members: group_id, account_id and, on added, added_by_account_id. For resource access: resource_type, resource_id, principal_kind and principal_id; granted adds level (its name, such as viewer) and workspace_id.

    Examples¶

    Grant a workspace role and check it¶

    A shared editor template (tier workspace, no owner), granted to account 42 in workspace 7 of the default tenant:

    from msflib.authz import PERMISSION_REGISTRY, PrincipalKind, RoleService, RoleTier
from msflib.authz.models import RoleAssignmentScope, RoleAssignmentCreate, RoleCreate

PERMISSION_REGISTRY.register("docs.publish")
service = RoleService()

editor = service.ensure_role(
    session, data=RoleCreate(key="editor", name="Editor", tier=RoleTier.workspace)
)
service.add_permissions(session, role_id=editor.id, permission_keys=["docs.publish"])
service.grant(
    session,
    data=RoleAssignmentCreate(
        role_id=editor.id, principal_kind=PrincipalKind.user, principal_id="42"
    ),
    scope=RoleAssignmentScope(tenant_id=tenant_id, workspace_id=7),
)

service.has_permission(
    session, account_id=42, tenant_id=tenant_id, workspace_id=7, permission_key="docs.publish"
)  # True
service.has_permission(
    session, account_id=42, tenant_id=tenant_id, workspace_id=8, permission_key="docs.publish"
)  # False: workspace roles do not reach other workspaces

    RoleCreate and RoleAssignmentCreate hold only what a client may send. The values the server decides are separate parameters: owner=RoleOwner(...) (default SHARED) for a role, scope=RoleAssignmentScope(...) (default UNSCOPED) for an assignment, and granted_by_account_id / created_by_account_id for the actor. Build them in the endpoint from the request context; never read them from the body.

    Granting the same role without workspace_id raises ValueError ("tier=workspace requires both tenant_id and workspace_id set"), because a workspace-tier role needs a workspace.

    Guard a route with a permission¶

    A document-publishing feature, end to end. The module owns the key; the host app seeds and grants.

    from fastapi import Depends
from msflib.authz import PERMISSION_REGISTRY, PrincipalKind, RoleService, RoleTier
from msflib.authz.models import RoleAssignmentScope, RoleAssignmentCreate, RoleCreate
from msflib.authz.seed import seed_role_permissions, seed_system_roles

# 1. The feature registers its key at import time (not in a function).
PERMISSION_REGISTRY.register("docs.publish")  # workspace-level only: no tenant cascade

# 2. At startup, after every module is imported: seed roles and bundle keys.
roles = seed_system_roles(session, default_tenant_id=tenant_id)
seed_role_permissions(session, roles=roles)  # the seeded workspace owner and admin get docs.publish

# 3. Optionally, a custom workspace role that can publish and nothing else.
service = RoleService()
editor = service.ensure_role(
    session, data=RoleCreate(key="editor", name="Editor", tier=RoleTier.workspace)
)
service.add_permissions(session, role_id=editor.id, permission_keys=["docs.publish"])

# 4. Grant it to account 42 in workspace 7.
service.grant(
    session,
    data=RoleAssignmentCreate(
        role_id=editor.id, principal_kind=PrincipalKind.user, principal_id="42"
    ),
    scope=RoleAssignmentScope(tenant_id=tenant_id, workspace_id=7),
)

# 5. Guard the route (authz comes from get_authz_dependencies, see above).
@router.post("/{workspace_slug}/docs/{doc_id}/publish")
def publish(doc_id: int, _: bool = Depends(authz.require_permission("docs.publish"))): ...

    What happens for account 42:

    Request Result Why
    publish in workspace 7 allowed editor is held in exactly that workspace and bundles docs.publish
    publish in workspace 8 403 a workspace role does not reach other workspaces
    a tenant-tier admin publishes in workspace 7 403 docs.publish is not tenant_cascade; hold a workspace role, or register the key with tenant_cascade=True
    the seeded workspace owner publishes in workspace 7 allowed seed_role_permissions bundled the key into owner

    The same key also reads naturally in code: service.has_permission(session, account_id=42, tenant_id=tenant_id, workspace_id=7, permission_key="docs.publish") returns True for the first row.

    For a tenant-wide action, register the key with tenant_cascade=True if tenant admins should reach it in every workspace, and guard with tier="tenant":

    PERMISSION_REGISTRY.register("docs.audit", tenant_cascade=True)

@router.get("/audit", dependencies=[Depends(authz.require_permission("docs.audit", tier="tenant"))])
def audit(): ...

    Troubleshooting¶

    • A role is assigned but grants nothing. The assignment is not effective. Check, in order, that its tenant_id / workspace_id match the role's tier (platform: none; tenant: tenant only; workspace: both), that they lie inside the role's owner, and that expires_at has not passed. Rows written through a raw action are not validated, and resolution silently ignores a bad one.
    • ValueError from grant. The message names the rule that failed: tier shape, owner scope, a missing role, an expires_at that is not in the future, or an existing unexpired assignment (AssignmentExistsError).
    • Two processes seeded at once. Seeding and the backfills use ensure_role / ensure_assignment, so concurrent startups converge on the same rows instead of failing on the unique index.
    • A workspace admin does not pass require_role(RoleKey(RoleTier.tenant, "admin")). Intended. The tier is part of the key; ask for the workspace-tier key, or use require_permission.
    • A tenant admin cannot act in a workspace. Tenant roles reach workspaces only for permissions registered with tenant_cascade=True. Otherwise grant a workspace-tier role in that workspace.
    • A new permission is missing from root or admin. seed_role_permissions bundles the keys registered when it runs. Run it after every module has been imported.
    • A role's key, tier or owner cannot be changed. They are immutable because changing them would reinterpret existing assignments. Create a new role and move the assignments.
    • Revoking an assignment did not remove access to an auth route. RoleCheck and WorkspaceRoleCheck read the attribute, not assignments. Authz guards honour the revoke.
    • Requests are denied with no tenant. get_current_tenant is wired but returned nothing. A missing request tenant is denied, never defaulted.
    • A backfill removed assignments it should not have. It treats its input as the complete set. Pass every account or membership.
