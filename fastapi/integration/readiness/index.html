    Readiness checks¶

    A deployment can be "up" and still unable to do its job: the queue broker rejects the password, an extension exists on the server but not in the application's database, a provider key was never exercised. The readiness engine in msflib.core.readiness answers one question before traffic arrives: which requirements are met, which are not, and what to do about it.

    • A check tests one requirement. It is read-only.
    • A remedy applies the safe, idempotent fix for the checks it names.
    • Each module may ship the checks for the capability it provides; the application adds its own and chooses the profile.

    Run it¶

    python -m msflib.core.readiness --suite app.readiness:suite --profile prod
python -m msflib.core.readiness --suite app.readiness:suite --fix        # asks first
python -m msflib.core.readiness --suite app.readiness:suite --json
    Option Effect
    --profile dev\|prod Severity and applicability: some checks only matter in production
    --only a,b Run only these groups or check ids, plus everything they require (a prerequisite that did not run could not fail). A name that matches no check or group is an error, never a green run
    --list List the checks (with what they require) and the remedies, run nothing; with --json, as data
    --offline Skip checks that call a paid external service; the run then carries a run.offline warning naming them, so it is never a plain READY
    --frontend-origin URL Also verify the origin against BACKEND_CORS_ORIGINS
    --fix Plan and apply the safe remedies, then re-check. Shows what each remedy will change (its preview; core.migrate names the pending revisions), then asks; --yes skips the question but not the preview, --dry-run only shows the plan
    --json Versioned machine-readable report (schema_version). With --fix it needs --yes or --dry-run (nothing can ask), applies the fixes, re-checks, and prints one document including fixes_applied (only what ran; [] when nothing was applied) and fixes_not_applied (remedies that were skipped as not runnable here, or only shown by --dry-run, each with its state)
    --settings module:attr Checks of the settings only (no database engine): the database checks are skipped, as for any suite built without an engine, so the report carries a run.no_engine warning and a clean run is READY (with warnings), exit 10, never 0 (in the text, the JSON and the exit code alike). Use --suite with an engine for a full check
    --verbose Include the library log output that is normally captured
    --isolation auto\|process\|thread Where a check that can hang runs. auto (default) is a killable worker process on Linux and a thread elsewhere; on macOS, pass process to get the worker (see Worker processes)

    Exit codes: 0 ready, 10 ready with warnings, 1 not ready. Warnings use 10 so a deploy pipeline can distinguish them.

    The report lists every check by group, then Needs attention (root causes first, with what each one blocks and how to fix it), then Next steps in the order they must be done.

    Wire it into an application¶

    # app/readiness.py
from msflib.core.readiness import Suite

from app.core.config import settings
from app.db.migrations import MIGRATION
from app.db.session import engine

suite = Suite.from_settings(
    settings,
    engine=engine,
    migration=MIGRATION,                       # a msflib.db.migrations.MigrationConfig
    migrate_command="python -m app.initial_data",  # optional: named in the guidance
    unmanaged_tables=["langchain_pg_*"],       # tables the models do not own
    name="my-app",
)

    Suite.from_settings collects core's own checks plus <package>.readiness.registry of every module whose settings class the application settings inherit. A module with no readiness checks is skipped; one whose checks fail to import is reported as a failing check, not hidden.

    Worker processes

    A check runs in a forked worker process that is killed when its timeout passes, so a hung check cannot keep logging, warning or writing to the context afterwards. The worker sees the suite as it is; what it returns (the outcome, the ctx.cache / ctx.facts entries it added, changed or removed, and the secrets it fetched) is pickled back. A change made in place to a picklable entry (appending to a cached list) is carried back too. Keep the values you store picklable: an unpicklable value the check sets is dropped, and one the check did not set stays as it was in the caller, so a change made inside it is not seen. The worker also gives any database engine in the cache or facts its own connections; it looks 12 levels deep and through 20,000 objects, and if it has to stop sooner it adds a warning to the check's log, so keep engines near the top of what you store. Isolation is used on Linux. On other platforms a check runs on a thread, which can time out but cannot be stopped, so its late output is not contained there; Context(isolation=...) chooses ("auto", "process", "thread"), and the command line has --isolation. On macOS, run with --isolation process to get the same containment as on Linux: a timed-out check is killed and cannot log or print afterwards. Auto does not pick it there because macOS system libraries are not always fork-safe; if a worker crashes with an Objective-C "fork() was called" message, set OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES for the run, or stay on the thread default. An in-memory or file SQLite engine used in thread mode needs connect_args={"check_same_thread": False}.

    What core checks¶

    Id Group Checks
    config.env_file config the settings' env file exists
    config.environment config ENVIRONMENT matches the profile (the --reset guard only protects production)
    config.secret_key config SECRET_KEY is set explicitly (it is random per start otherwise)
    config.cors config the frontend origin is allowed
    db.reachable database the database answers
    db.dialect database SQLite is only acceptable outside production
    db.migrations database schema is at head and nothing is missing (see below); a suite with an engine but no MigrationConfig gets a warning, not a silent skip
    db.unmanaged database objects outside the models (information only)
    storage.directory storage the upload directory exists and is writable (read-only check)

    Remedies: core.migrate, storage.create_directory.

    core.migrate runs the application's own revision scripts, so it is not unconditionally safe. Before --fix applies it, the pending revisions are rendered to SQL with Alembic's offline mode (no database; msflib.db.offline.render_upgrade_sql, classified in checks/migration_risk.py; msflib.db.sqltext splits statements and hides literals) and that SQL is classified, whatever Python produced it. A statement is safe only when it is recognisably additive: CREATE TABLE, CREATE INDEX, CREATE EXTENSION, INSERT ... VALUES into a table the same upgrade creates (never through DEFAULT, which can run a column default function), ALTER TABLE ... ADD ..., SET/DROP NOT NULL or DEFAULT, and the revision stamp. DROP, DELETE, TRUNCATE, UPDATE of data, a column type change, CALL/SELECT of a function and anything else it does not recognise make the remedy "cannot run here" with the first words of the statement and its revision. So does a revision that cannot be rendered without a database (it queries one, imports something missing, or uses a type that does not compile) and an env.py that is not just imports, plain name bindings and a top-level run_alembic_env(...) call (it is parsed, so the name in a string or an unreachable branch does not count), because the code it runs is not reviewed. A statement with an allowed verb is still left to a person when it runs a query or a function that is not known to be harmless (CREATE TABLE ... AS SELECT, INSERT ... SELECT, DEFAULT purge_all()); now(), gen_random_uuid() and similar are fine. Only Alembic's own BEGIN (first) and COMMIT (last) are accepted; a transaction statement from a revision, such as an early COMMIT, is left to a person. A quoted or schema-qualified call ("purge_all"(), public.purge_all()) counts as a call; now() is trusted only unqualified or as pg_catalog.now(). The version table may only be changed by Alembic's own stamp of the step being rendered, and every pending revision must appear in the rendered upgrade (pending revisions on two branches are left to a person). A revision that asks whether it is being rendered (is_offline_mode(), as_sql, in its own source or in a local module it imports) is left to a person; this reads source, so a probe built at run time is not seen, since what it renders is not what it runs. Rendering imports the revisions and runs their upgrade() offline, so top-level or upgrade() side effects of a revision run when the plan is built, not only under --fix. A new, empty database is never blocked: there is nothing to lose. The operator reviews the revision and runs the application's migration command themselves (named in the guidance when the suite is built with migrate_command=). The classification is conservative, not a proof: any doubt means a person. It is a safety net against an accidental destructive migration, not a security boundary: whoever can merge a revision can already run arbitrary code through its upgrade(). Known limits: the gate trusts operators by symbol (||, +, =), but PostgreSQL picks an operator by operand types, so an expression on an existing table (an index or CHECK) whose column has a user-defined type with a side-effecting operator is not caught; defining that type, operator and function is itself held, so it takes an earlier reviewed migration. Treat an additive result as "nothing recognisably destructive", and read migrations that define custom types or operators yourself.

    Drift is classified¶

    db.migrations does not treat every difference as failure. A missing or changed managed object (a table, column or type the models expect) fails. An object the models do not declare (LangChain's PGVector tables, an extension's catalog) is information, listed by db.unmanaged, and never fails the run. List what the application does not own in unmanaged_tables (glob patterns); those are ignored entirely.

    A pre-tenancy string tenant_id column is recognised, and the guidance points at scripts/migrate_tenant_id_columns.py, the one-time converter, rather than suggesting the database be recreated.

    Write a check¶

    # msflib/<module>/readiness.py  (or app/readiness.py for the application's own)
from msflib.core.readiness import Outcome, Registry, RemedyResult, Safety, Step

registry = Registry("knowledge")


@registry.check(
    "knowledge.age.usable",
    title="AGE is usable by the application role",
    group="database",
    requires=("db.reachable",),                      # BLOCKED, not FAIL, if that failed
    when=lambda ctx: ctx.get_setting("GRAPH_BACKEND") == "age",
)
def age_usable(ctx):
    try:
        ctx.run_sql("SELECT '{}'::agtype")
    except Exception as exc:
        return Outcome.fail(
            f"{type(exc).__name__}",
            steps=[Step.run('psql -d <db> -c "CREATE EXTENSION age;"')],
            remedies=("knowledge.provision",),
        )
    return Outcome.succeed()


@registry.remedy("knowledge.provision", title="create the AGE extension and grants",
                 fixes=("knowledge.age.usable",), safety=Safety.SAFE,
                 ready=lambda ctx: None if ctx.get_secret("SUPERUSER_DSN") else "needs a superuser DSN")
def provision(ctx):
    ...
    return RemedyResult(True, "provisioned")

    Rules:

    • Checks are read-only. A probe that mutates must run in a transaction that is rolled back.
    • Declare what you need with requires, so one root cause is reported once and its dependents are BLOCKED.
    • Use ctx.get_secret(name, namespace="MODULE") for secrets (the namespace is the module's settings scope; omit it for a flat settings object). Anything a check reports (detail, steps, evidence, captured log lines, remedy reasons) is masked: URL passwords, every fetched secret, and the values under sensitive keys (password, token, ... from msflib.core.pii), recursively.
    • Warnings count. A log record at WARNING or above, or a Python warning, emitted by a check's worker turns a PASS into a WARN (exit code 10); INFO and DEBUG never change the verdict. A check whose library is known to be noisy sets promote_warnings=False. Output is attributed to the check whose worker emitted it; a killed worker has no late output.
    • isolated=False runs a check in the calling process, with no timeout, for a check that only reads settings and starts no threads. Three checks use it: config.environment, config.secret_key and config.cors; the other config.* checks, such as config.env_file, probe the filesystem, which can hang, and stay isolated. The default is isolated. In the calling process, print, logging and warnings are collected and masked, but text written straight to a file descriptor or to sys.__stdout__ is not: only a check that never writes output belongs here.
    • Remedies are captured too. A remedy's ready() and preview() (60 s limit each) and apply() also run in a worker, so they cannot change Python state in the caller beyond ctx.cache / ctx.facts; what they change must be in the database, the filesystem or another process. Their log output and warnings are masked and returned with the plan or in fixes_applied[].log; nothing reaches stdout, so --fix --yes --json stays one document. One exception: when the suite's engine is an in-memory SQLite database, apply() runs in the calling process, with no timeout and no isolation, because a worker's writes to its copy of that database would never reach the caller. Such a remedy can change any Python state in the caller, so keep it to the database. ready() and preview() still run in a worker.
    • A check that timed out gets no automatic remedy: it did not finish, so what is wrong is unknown. Re-run once the cause is fixed.
    • Read core settings with ctx.get_setting(name, namespace="CORE") and test explicit values with ctx.is_explicitly_set(name, namespace="CORE"), so the checks see the same values in the flat and the nested settings layouts.
    • Fetched secrets shorter than four characters are masked as whole tokens, so a password such as pw is hidden without rewriting words that contain it.
    • A when predicate that raises is a FAIL, not a skip: a broken predicate must not make a deployment look ready.
    • Name functions with a verb (check_broker, get_scope): the checks in core and the modules follow this.
    • Remedies are idempotent, never drop or delete, and declare safety, which has no default: a remedy that does not say what it can change cannot be registered. DESTRUCTIVE remedies are listed as manual and never applied by --fix.
    • Check ids starting run. are reserved for the findings the run adds about what it skipped (run.offline, run.unverified, run.no_<resource>); a suite with such a check is rejected.
    • A check that returns Outcome.skip is saying it could not verify its requirement, so the run carries a run.unverified warning naming it. For a requirement that simply does not apply, use when= (or profiles= / needs=), or Outcome.inform for a note; do not skip from inside.
    • Mark paid calls with paid=True so --offline skips them, and declare the suite resource a check cannot run without with needs=("engine",) (or "migration"): when it is missing the check is skipped and the run carries a run.no_<resource> warning naming it.
    • Import heavy optional dependencies (redis, celery) inside the check, and never import the application from a module's checks.
    • A check has a timeout (timeout=, default 60 s); a hung check is a finding, not a hang. A check's when predicate runs under the same timeout, and the check gets only what is left; when the predicate used nearly all of it, the check fails with "not run" instead of being started.

    Output the report as data¶

    Report.to_dict() (and --json) is versioned (schema_version): verdict, exit_code, counts, findings[] (id, status, severity, detail, evidence, steps, remedies, blocked_by, log lines captured while the check ran), plan[], manual[] and unattributed_log[] (output captured outside any check, such as a remedy's ready()).
