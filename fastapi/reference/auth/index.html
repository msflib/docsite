    msflib.auth.eventbus ¶

    register_event_hooks(*, emitter: AppEmitter, settings: SettingsBase, token_store: StoreInterface, send_code_email_override: Callable | None = None) -> None ¶

    React to what happens to an account outside the auth router.

    • Registered: send the email verification code. Does nothing unless SEND_VERIFICATION_ON_REGISTRATION is true, so the setting can change without rewiring.
    • Email changed: everything issued for the old email stops working (access tokens, the pending reset, pending codes), so it cannot be used on an account that takes that email later. Needs changes in the event, which msflib-account sends. If this fails (the key store is down), the error is raised and msflib-account undoes the update. The old email stays locked from the cleanup until the update is committed, and the auth router takes the same lock to issue anything, so nothing issued in between survives. An update that is rolled back after the cleanup leaves the lock until it expires (EMAIL_LOCK_HOLD_SECONDS).

    Call at application startup; a second call on the same emitter replaces the first. Pass the same token_store as the auth router, which checks what is sent here.

    msflib.auth.resolvers ¶

    Workspace resolution strategies for msflib.auth.

    A WorkspaceResolver determines how the current workspace is identified from an incoming request. The strategy is chosen once at app startup and injected into get_user_dependencies().

    Built-in resolvers¶

    • PathParameterResolver — extracts a path parameter (default: workspace_slug). This matches the original hard-coded behaviour and is the recommended starting point.
    • HttpHeaderResolver — reads a request header (default: X-Workspace). Useful for API clients or SPAs that send the active workspace as a header rather than encoding it in the URL.

    Custom resolvers¶

    Subclass WorkspaceResolver and implement resolve() to support any other strategy (request header, JWT claim, query param, etc.). See modules/auth/WORKSPACE_RESOLUTION.md for a full guide.

    msflib.auth.services ¶

    codes ¶

    Short one-time codes sent to an account: password reset, verification, login by code.

    The recipient is the address the code goes to. Today that is an email; nothing here depends on it, so a phone number works the same way.

    A six-digit code is easy to guess, so every use shares the same limits: one pending code per recipient and purpose, a short lifetime, few wrong guesses, single use, and a pause between sends.

    Every change to a record is written only over the record that was read (StoreInterface.put_if). So of several requests that arrive together, each wrong guess is counted once, a right code is accepted once, one request is sent a code, and a record that was replaced or used in between is never written back.

    PendingCode(code: str, created: float, expires: float, code_expires: float, attempts: int = 0, used: bool = False, data: dict[str, str] = dict()) dataclass ¶

    A code that was sent and not yet used. Times are UTC timestamps.

    Attributes:

    Name Type Description
    expires float

    when the record goes; later than code_expires when data outlives the code.
    used bool

    a right code or value was accepted, so nothing is accepted again.
    data dict[str, str]

    what the code stands for, when it is more than the code itself (the reset link).

    OneTimeCodeManager(store: StoreInterface, purpose: str, code_seconds: int, max_attempts: int, resend_seconds: int, record_seconds: int | None = None) dataclass ¶

    Issues and checks the codes of one purpose, kept in the key store as <purpose>:<recipient>.

    Attributes:

    Name Type Description
    purpose str

    what the code is for. A code works only for the purpose it was issued for.
    code_seconds int

    how long a code can be used.
    max_attempts int

    resend_seconds int

    record_seconds int | None

    how long the record is kept, when longer than code_seconds.
    issue(recipient: str, data: dict[str, str] | None = None) -> str | None ¶

    Replace any pending code for recipient with a new one and return it.

    Returns None, and issues nothing, when a code was issued less than resend_seconds ago, also when that happened in another request at this moment. A code that was used, or whose guesses are used up, still counts: the pause runs from when it was sent.

    discard(recipient: str, *, code: str | None = None) -> None ¶

    Drop the pending code of recipient, with the pause before its next one.

    With code, only while that is still the pending code: a newer one is left alone.

    verify(recipient: str, code: str, *, consume: bool = True) -> PendingCode | None ¶

    The pending record if code is right. A wrong code counts against it.

    A right code uses the record up. With consume=False (a check before the real use) a right code is only read, so nothing is written. After max_attempts wrong codes no code is accepted; the record stays until it expires or issue replaces it, so the pause between sends still applies.

    verify_data(recipient: str, name: str, value: str, *, consume: bool = True) -> PendingCode | None ¶

    The pending record if its data[name] is value (the password reset link token).

    Like verify, but a wrong value is not counted: these values are too long to guess.

    EmailLock(store: StoreInterface, wait_seconds: float, hold_seconds: int) dataclass ¶

    Lets one caller at a time issue for an email or change it.

    Issuing (a token, a code, a reset) holds it from looking up the account to storing what was issued; an email change holds it on the old email from the cleanup to the commit. So nothing issued for the old email can appear after the cleanup.

    release_async(email: str, owner: str) -> None async ¶

    SecondFactor ¶

    Bases: Protocol

    A second login step that the host supplies (an authenticator app, a code by SMS, ...).

    The router owns the order: a login is held for this step only after the password, or the identity provider, has been verified, and an access token is issued only after verify accepts a code for that login. Called with keyword arguments.

    required(*, session: Session, account: ModelBase, first_factor: FirstFactor) -> bool ¶

    Whether this account must pass a second factor after first_factor.

    A factor that proves the same thing as the first step adds nothing: one that sends its code by email should answer false after FirstFactor.email_code.

    challenge(*, session: Session, account: ModelBase) -> dict[str, Any] | None ¶

    Start the step (send a code, if the method needs one). The result goes to the client.

    verify(*, session: Session, account: ModelBase, code: str) -> bool ¶

    PendingLoginManager(store: StoreInterface, step: str, secret_key: str, lifetime_seconds: int, max_attempts: int) dataclass ¶

    Holds the logins that passed one step and wait for the next.

    The client holds a signed token; the store holds the wrong guesses so far under the token's id. A login that is not in the store cannot go on.

    Attributes:

    step str

    the step the logins wait for. It is the typ of the token and the prefix of the store key, so a token issued for one step cannot be claimed for another.
    lifetime_seconds int

    max_attempts int

    open(email: str, account_id: str) -> str ¶

    Hold a login for the account and return the token the client sends back.

    The token names the account by id as well as by email, so it cannot finish a login on another account that took the email in the meantime.

    claim(token: str) -> PendingLogin | None ¶

    Take the login a token stands for out of the store, if it is still waiting.

    Only one caller gets it, so requests that arrive together cannot share a guess. After a wrong code, give it back with reopen.
